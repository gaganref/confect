A backend declaration describes your Convex backend in four files beside your functions. `confect codegen` and `confect dev` then write `convex/convex.config.ts`, `convex/auth.config.ts`, `convex/http.ts`, `convex/confectHealth.ts` and `confect/_generated/manifest.ts` from it, so the env your handlers read, the env Convex validates, the env each mounted component receives and the env your infrastructure supplies all come from one place.

After upgrading to the fork based on upstream 10.3.1, run `confect codegen` again. The generator output changed; do not keep files emitted by the previous generator.

The declaration is opt-in. It applies when `confect/app.ts` exists. Without that file, you write `convex/convex.config.ts` yourself and `confect/auth.ts` and `confect/http.ts` keep their [existing forms](/concepts/project-structure).

| File              | Holds                                       | Codegen writes                                                         |
| ----------------- | ------------------------------------------- | ---------------------------------------------------------------------- |
| `confect/env.ts`  | `Env.make(name, { ... })`                   | The `env` of `convex/convex.config.ts`, and the manifest               |
| `confect/app.ts`  | `App.make({ env, mounts })`                 | `convex/convex.config.ts`, `convex/confectHealth.ts`, and the manifest |
| `confect/auth.ts` | `Auth.make(app, { providers })`             | `convex/auth.config.ts`                                                |
| `confect/http.ts` | `Http.make({ api, handlers, docs, guard })` | `convex/http.ts`, and with route specs `routes.ts` and `openapi.json`  |

## `env.ts`

`CONVEX_SITE_URL` and `CONVEX_CLOUD_URL` are [built-in addresses](/server/environment-variables#built-in-deployment-addresses) and cannot be declared as environment slots or bound by mounts.

Declare every environment variable the backend reads, once, with its backend's name:

```ts confect/env.ts
import { Env } from "@confect/core";

export default Env.make("tenant", {
  EMAIL_FROM: Env.string(),
  RESEND_API_KEY: Env.secret(),
  EMAIL_TRANSPORT: Env.literals(["resend", "log"]),
  PLATFORM_URL: Env.optional(Env.string()),
});
```

Each entry is an Effect `Config`. Import the env in a handler and yield an entry to read it:

```ts confect/emails.impl.ts
import * as Effect from "effect/Effect";
import env from "./env";

export const configuration = Effect.gen(function* () {
  const from = yield* env.EMAIL_FROM; // string
  const key = yield* env.RESEND_API_KEY; // Redacted<string>
  const transport = yield* env.EMAIL_TRANSPORT; // "resend" | "log"
  const platform = yield* env.PLATFORM_URL; // Option<string>
  return { from, key, transport, platform };
});
```

| Constructor           | Handler reads       | Convex validator               |
| --------------------- | ------------------- | ------------------------------ |
| `Env.string()`        | `string`            | `v.string()`                   |
| `Env.secret()`        | `Redacted<string>`  | `v.string()`                   |
| `Env.literals([...])` | one of the literals | `v.union(v.literal(...), ...)` |
| `Env.optional(entry)` | `Option<...>`       | `v.optional(...)`              |

The name is the backend's identity. An entry from one backend's env cannot be bound in another backend's mounts. For a [Confect-authored component](/server/components), the name is also the component's Convex name.

Reads resolve through Confect's [Convex-aware `ConfigProvider`](/server/environment-variables), as any other `Config` does. Import `env.ts` from handlers, never `app.ts`: `app.ts` imports component definitions, which load only in Convex's config analysis.

## `app.ts`

List the `convex.config` definitions of the Convex components the backend mounts, then its mounts. Each mount is declared in a file directly in `confect/`, such as its own `confect/<mount>.ts`, with [`Mount.make`](/server/components#reach-a-mounts-client), which takes the component's descriptor and its placement:

```ts confect/app.ts
import { App } from "@confect/core";
import workpool from "@convex-dev/workpool/convex.config.js";
import email from "@acme/email/convex.config.js";
import { BulkEmail } from "./bulkEmail";
import { ImportsPool } from "./importsPool";
import env from "./env";

export default App.make({
  env,
  components: [email, workpool],
  mounts: [BulkEmail, ImportsPool],
});
```

```ts confect/bulkEmail.ts
import { Mount } from "@confect/core";
import Email from "@acme/email/client";

export const BulkEmail = Mount.make(Email, {
  name: "bulkEmail",
  httpPrefix: "/bulk-email",
});
```

Set `requiresMiddleware` in `App.make` to require middleware on every registered function, including internal functions. Requirements are matched by middleware key. Codegen fails once with every uncovered function's group path and name. Generated registration also applies `GroupImpl.finalize({ required, groupPath })` when its layer builds. Attach middleware to each function or its own group. Raw Convex functions cannot satisfy this requirement. Mounted backends declare their own requirements; HTTP middleware is separate.

```ts
import { Policy, Trace } from "./middleware";
export default App.make({ env, requiresMiddleware: [Policy, Trace] });
```

Mount names `app` and `docs` are reserved for the root app and docs page. This is deliberately one rule for every mount, including a component's child mounts. Names are case-sensitive, so `App` and `DOCS` are accepted.

A standalone `Mount.make` call rejects either reserved literal at compile time. A call written inline in `App.make`, typed as `Mount.Any`, or placed in a `ReadonlyArray<Mount.Any>` literal widens the name to `string` and compiles. Codegen catches these names with `ReservedMountName`. It also catches a name supplied as a widened `string`. Rename an existing mount, for example to `application` or `docsWorker`, and update references to its name.

Each mount names itself. Codegen pairs it with the listed definition whose `defineComponent` name is its component's name, and writes one `app.use` per mount in list order. It fails, naming the mount or definition, when a mount's component has no listed definition, when a listed definition has no mount, when two mounts share a name, and when two listed definitions share a `defineComponent` name. `Mount.make` types `env` against the descriptor's env slots. These fail to typecheck:

- binding env on a root app's mount, including a constant
- binding an optional entry to a required slot
- binding a value outside a literal slot's values
- binding a slot the component does not declare
- binding an entry from another backend's env (reported at `App.make`)

A root app's mounts are placement only. Leave their slots open and supply each stage's values through the deployment stack. `App.make` refuses a root mount that binds env, and codegen reports `RootMountEnv` if types were bypassed.

A component may bind its child's slot to a constant or a compatible entry of its own env. Any slot may remain open, even a required one. Codegen promotes each open slot to `<MOUNT>_<SLOT>`. It splits lowercase-to-uppercase and digit-to-uppercase boundaries, and the last capital of an acronym before a lowercase letter, then uppercases the name. For example, `HTTPServer`, `myHTTPClient` and `s3Bucket` become `HTTP_SERVER`, `MY_HTTP_CLIENT` and `S3_BUCKET`. Mount `bulkEmail` with slot `RESEND_API_KEY` becomes `BULK_EMAIL_RESEND_API_KEY`. A child's open slot can pass through several parents as `BULK_EMAIL_CHILD_RESEND_API_KEY`.

A derived name that duplicates a declared variable or another open slot fails with `DerivedSlotCollision`. For example, mounts `aB` and `a_b` both promote `TOKEN` to `A_B_TOKEN`. Rename a mount or slot to resolve the collision. `httpPrefix` reserves the mounted Convex component's routes. A name such as `_bulk` that derives a variable without a leading letter fails with `InvalidDerivedEnvKey`, which names the mount and slot. Derived variables also pass `Env.validateKey`; mount `convex` with slot `SITE_URL` cannot replace the built-in `CONVEX_SITE_URL`.

Renaming a mount changes its derived deployment variable names. The values live in your stack file, typed by the generated manifest. Regenerate the manifest and update the stack's mount settings together.

The [generated test registry](/guides/testing) discovers a mounted Convex component's test kit at `<package>/testing`, then `<package>/test`, unless the component's descriptor names one with `testing`. Mounts do not accept a `testing` option.

Codegen writes the matching Convex definition:

```ts convex/convex.config.ts
// Generated by `confect codegen` from confect/app.ts. Do not edit.
import { defineApp } from "convex/server";
import { v } from "convex/values";
import workpool from "@convex-dev/workpool/convex.config.js";
import email from "@acme/email/convex.config.js";

const app = defineApp({
  env: {
    EMAIL_FROM: v.string(),
    RESEND_API_KEY: v.string(),
    EMAIL_TRANSPORT: v.union(v.literal("resend"), v.literal("log")),
    PLATFORM_URL: v.optional(v.string()),
    BULK_EMAIL_FROM: v.string(),
    BULK_EMAIL_RESEND_API_KEY: v.string(),
    BULK_EMAIL_TRANSPORT: v.union(v.literal("resend"), v.literal("log")),
  },
});

app.use(email, {
  name: "bulkEmail",
  httpPrefix: "/bulk-email",
  env: {
    FROM: app.env.BULK_EMAIL_FROM,
    RESEND_API_KEY: app.env.BULK_EMAIL_RESEND_API_KEY,
    TRANSPORT: app.env.BULK_EMAIL_TRANSPORT,
  },
});

app.use(workpool, {
  name: "importsPool",
});

export default app;
```

A Confect-authored component declares itself with `App.make({ kind: "component", env, components, mounts })`, with `env.ts` and `app.ts` in its own `confect/` directory. `confect codegen --component-dir` writes its `defineComponent(name, { env })`. The kind defaults to `"app"`; codegen rejects a declaration whose kind differs from the target directory. Components can mount other components, but `Auth.make` accepts only app declarations.

## `auth.ts`

Declare the identity providers whose tokens the backend accepts. This is Convex's own [provider list](https://docs.convex.dev/auth/advanced/custom-auth). Use `Auth.siteUrl` for the deployment's site URL and `Auth.cloudUrl` for its cloud URL. `domain`, `issuer`, `jwks` and `applicationID` also accept required `Env.string()` or `Env.literals(...)` entries from this backend:

```ts confect/auth.ts
import { Auth } from "@confect/core";
import app from "./app";
import { BulkEmail } from "./bulkEmail";

export default Auth.make(app, {
  providers: [
    { domain: "https://login.example.edu", applicationID: "tenant" },
    {
      type: "customJwt",
      applicationID: "tenant",
      issuer: Auth.siteUrl(),
      jwks: Auth.siteUrl(BulkEmail, "/.well-known/jwks.json"),
      algorithm: "RS256",
    },
  ],
});
```

Codegen writes `convex/auth.config.ts` with deployment URLs as `process.env.CONVEX_SITE_URL` or `process.env.CONVEX_CLOUD_URL` expressions and env entries as `process.env["KEY"]!`. It never reads env values during generation. Optional entries and secrets are rejected. The output uses `satisfies AuthConfig`. Components cannot declare `auth.ts`.

For deployment-signed JWTs, use `Auth.cloudUrl("/components/auth")` as the issuer, `Auth.cloudUrl("/.well-known/jwks.json")` as the JWKS, and `"ES256"` as the algorithm. `Auth.siteUrl()` can supply the receiving deployment's `applicationID`; a session provider can keep `"convex"`. Cloud URL paths are explicit because component issuer paths differ from HTTP mount prefixes.

### Runtime provider data

An optional `family` and `name` on each provider are application-defined strings.
Codegen omits them from Convex's auth config and writes
`confect/_generated/auth.providers.ts` for handlers:

```ts
import { providers } from "./_generated/auth.providers";
```

Each entry has `issuer` (the provider's `issuer` or `domain`), `audience` when
`applicationID` is present, and the declared `family` and `name`. URL and env
expressions resolve in the deployment. The generated module imports nothing, so
handlers can classify verified identities without importing `auth.ts`, `app.ts`,
or component definitions. Existing providers need no metadata. Removing `auth.ts`
removes both generated auth files.

### Provider families

`Auth.family` declares a set of `customJwt` providers whose issuers come from one
env value. Adding or removing an issuer is an env change. You don't edit
`auth.ts`, run codegen or redeploy.

```ts confect/auth.ts
export default Auth.make(app, {
  providers: [
    { domain: "https://login.example.edu", applicationID: "tenant" },
    Auth.family({
      family: "service",
      issuers: env.PEER_SERVICES,
      algorithm: "ES256",
    }),
  ],
});
```

`issuers` takes a required `Env.string()` entry of this backend. Its value is a
JSON array with one object per issuer:

```json PEER_SERVICES
[
  {
    "name": "platform",
    "issuer": "https://platform.convex.cloud/components/auth",
    "jwks": "https://platform.convex.cloud/.well-known/jwks.json",
    "applicationID": "https://tenant.convex.site"
  }
]
```

`name`, `issuer` and `jwks` are required. `applicationID` is the audience Convex
checks, and it is optional, as in Convex's own `customJwt` provider. Other fields
are refused. A misspelled `applicationId` fails the value instead of dropping the
audience check.

Codegen writes `auth.config.ts` to read `process.env["PEER_SERVICES"]` and expand
it with `AuthFamily.config`, so the value never reaches codegen. Convex
evaluates `auth.config.ts` against the deployment's env on every push. It also
evaluates it again when an env variable changes, in the same transaction. An
invalid value therefore fails the push, and an env change that would make it
invalid is refused with Convex's "This change would make the auth config
invalid" error. Each expanded provider is checked against every other provider.
An issuer that a family shares with another provider, in the family or out of it,
fails the push too. Convex compares issuers after it adds a missing `https://`
and trims trailing slashes, and so does the check. Two static providers may still
share an issuer with different audiences, as Convex allows.

With a family, `confect/_generated/auth.providers.ts` exports `providers` as a
function. Each call reads the value from the deployment's env with the same
parser, `AuthFamily.providers`. Each member has `issuer`, `audience` when it
has an `applicationID`, the family's `family` and its own `name`. An invalid
value lists no member, so no peer matches. Match a verified identity with
`AuthFamily.lookup`:

```ts
import { AuthFamily } from "@confect/core";
import { providers } from "./_generated/auth.providers";

const match = AuthFamily.lookup(providers(), identity.issuer);
// { _tag: "Unknown" } | { _tag: "Provider", provider } | { _tag: "Shared", providers }
```

`Shared` carries every provider of an issuer that two providers share, so a
guard never gets one provider for an ambiguous issuer. Codegen refuses two
families that read one env value. A family with no issuers is invalid. Remove
the declaration to stop accepting the family.

Call `providers()` where you match, not once at the top of a module. A query or
mutation reads env through its transaction, so the read joins its dependencies.
A Node action keeps modules it shares with other actions loaded across an env
change, so a list built when the module loaded would keep the old peers. Read on
each call, every function sees a changed env value without a redeploy. A
backend without a family keeps `providers` as a constant list.

## `http.ts`

Declare the backend's own `HttpApi` and its handlers. `docs` is optional and serves a Scalar page for the api at that path:

```ts confect/http.ts
import { Http } from "@confect/core";
import { TenantApi, TenantHandlers } from "./api";

export default Http.make({
  api: TenantApi,
  handlers: TenantHandlers,
  docs: "/docs",
});
```

Every route is an `HttpApi` endpoint. Codegen writes `convex/http.ts`, which serves it through [`HttpRouter`](/server/http-api):

```ts convex/http.ts
// Generated by `confect codegen` from confect/http.ts. Do not edit.
import { HttpRouter } from "@confect/server";
import schema from "../confect/_generated/schema";
import http from "../confect/http";

export default HttpRouter.make(schema, http.routes, { api: http.api });
```

The schema supplies the backend's capabilities; `{ api }` supplies endpoint labels for Convex logs and the dashboard. Mounted components serve their own routes under their prefixes; your middleware does not run in front of them.

Codegen fails when an app route or the docs page is at or under a mount's prefix, because Convex accepts such a route and lets it silently shadow the component's. It also fails when two of the backend's own routes share a method and path, or when two mount prefixes overlap. Prefix checks run even without `http.ts`. Each Convex component checks its own routes during codegen.

### Route specs

A backend whose specs declare [route specs](/server/http-api#route-specs-and-their-guard) names their guard in `http.ts`. One that serves only route specs leaves out `api`, `handlers` and `docs`:

```ts confect/http.ts
import { Guard, Http } from "@confect/core";

export default Http.make({ guard: Guard.none });
```

`api` and `handlers` go together, and `docs` needs them. The types refuse part of an api, and when part of one reaches `Http.make` through an untyped value, it throws `PartialApi` and codegen fails to load `confect/http.ts` with that message.

Codegen refuses route specs when `http.ts` is missing, or when its `guard` is missing or was not made with `Guard.make`. `Guard.none` is the explicit choice to serve routes with no admission. A backend without `app.ts` cannot serve route specs, so codegen refuses them there too.

Codegen serves route specs from the same `convex/http.ts`. It writes `confect/_generated/routes.ts`, which hands [`Routes.make`](/server/http-api#route-specs-and-their-guard) every leaf that declares one, and the router serves `http.ts`'s endpoints and the route specs together, behind the guard `http.ts` names:

```ts convex/http.ts
// Generated by `confect codegen` from confect/http.ts. Do not edit.
import { HttpRouter } from "@confect/server";
import * as Layer from "effect/Layer";
import schema from "../confect/_generated/schema.js";
import http from "../confect/http.js";
import routes from "../confect/_generated/routes.js";

export default HttpRouter.make(
  schema,
  Layer.merge(http.routes, routes.routes),
  { api: [http.api, routes.api], guard: http.guard },
);
```

A backend with `confect/runtime.ts` also passes `observability`, as it does without route specs. A component serves its route specs from its own `convex/http.ts`, under the HTTP prefix of each mount that installs it, which is the path its host's manifest lists.

Codegen also writes `confect/_generated/openapi.json`, an OpenAPI 3.1 document of the route specs alone. `http.ts`'s `docs` page still documents its own endpoints. Codegen reads every route while writing the document, so a route error without an `HttpApiSchema.status` fails codegen at the spec that declares the route, naming the route and the error. Once the last route spec goes, codegen removes `routes.ts` and `openapi.json` and writes the same `convex/http.ts` as a backend that never had one.

Codegen checks route specs with the backend's own routes, by method and path with parameter names ignored, and against every mount prefix. It catalogues each one in the manifest under `http.app`, by the spec's module path and the route's name, such as `http.app.echo.say`, so a component's route specs reach its host's manifest under the mount. A route spec is never a Convex function. A leaf that holds only route specs gets no `convex/` module and no registration file, and a mixed leaf's module exports only its Convex functions.

A GET or OPTIONS route reads its args from the query string, and every route reads its path parameters from the URL. Codegen accepts such an arg only when each of its values comes back from the URL unchanged. A path parameter must be required and encode as one string. Strings, refined and branded strings, string literals, enums and template literals qualify, as do numbers, booleans, dates and other schemas whose encoded side is one string, also through `Schema.suspend`. A query arg may also be an array or a tuple of such strings, which the URL repeats under one key, when no element is optional or `undefined`. An optional query arg may be left out. A union qualifies only when no member's string can read as another member's value, so `Schema.NullOr(Schema.String)` and a union of a string with a number, a boolean or an array are refused. So are structs, records, nested arrays, `undefined`, `Schema.Unknown` and `Schema.Any`. An accepted array still cannot send an empty list, since the URL leaves the key out and the server answers 400. Declare `Schema.NonEmptyArray` when an empty list is not a value. A URL carries UTF-8, which has no lone UTF-16 surrogate, so one such as `"\uD800"` in a query string, a query array element or a `Schema.StringFromBase64` value reaches the handler as `"�"`. A plain string path parameter holding one fails in Effect's client instead. Every string argument has this loss.

## The manifest

`confect/_generated/manifest.ts` is plain data with no imports. Infrastructure that deploys the backend reads it instead of backend code:

```ts confect/_generated/manifest.ts
export default {
  format: 1,
  sections: {},
  name: "tenant",
  env: {
    EMAIL_FROM: { kind: "string", optional: false },
    RESEND_API_KEY: { kind: "secret", optional: false },
    EMAIL_TRANSPORT: {
      kind: "literals",
      values: ["resend", "log"],
      optional: false,
    },
    PLATFORM_URL: { kind: "string", optional: true },
  },
  mounts: {
    bulkEmail: {
      component: "email",
      httpPrefix: "/bulk-email",
      env: {
        FROM: { kind: "string", optional: false, variable: "BULK_EMAIL_FROM" },
        RESEND_API_KEY: {
          kind: "secret",
          optional: false,
          variable: "BULK_EMAIL_RESEND_API_KEY",
        },
        TRANSPORT: {
          kind: "literals",
          values: ["resend", "log"],
          optional: false,
          variable: "BULK_EMAIL_TRANSPORT",
        },
      },
    },
    importsPool: { component: "workpool", env: {} },
  },
  http: {
    app: {
      health: {
        ready: {
          method: "GET",
          path: "/health/ready",
          owner: "app",
          group: "health",
          endpoint: "ready",
          digest: "sha256:...",
        },
      },
    },
    bulkEmail: {
      webhooks: {
        resend: {
          method: "POST",
          path: "/bulk-email/webhooks/resend",
          owner: "bulkEmail",
          group: "webhooks",
          endpoint: "resend",
          digest: "sha256:...",
        },
      },
    },
  },
  digest: "sha256:...",
} as const;
```

A declared component writes the same format 1 manifest. Package it with the component and pass it to `Component.make(name, { manifest, client })`. The host reads it without loading backend code. Format 1 is closed. Readers refuse wrong or missing fields, unknown fields and unknown slot kinds with `UnsupportedManifestFormat`, which names the file or import. They also refuse a provider tag whose `selector` is not a `providers` slot of its own record offering the tag's provider, a malformed or reserved `variable`, a route leaf whose `owner`, `group` or `endpoint` differs from its keys, and a leaf `digest` that differs from the root digest. A manifest of a later format asks you to upgrade the Confect packages that read it; any other refusal asks you to regenerate with `confect codegen`. Keep component and host generators on the same release as the reader. Repeated `values` entries are refused. A `providers` slot or any slot with a `provider` tag cannot be automatic. A shape change requires the next format number.

Extension data lives only in `sections`, including section names that match built-in fields. A section owns the format and JSON structure of its data. A component without a manifest preserves string literal unions and redacted schemas as literal and secret slots. Every other legacy schema becomes a string slot.

`Manifest.Values` types the values a deployment supplies. A missing required variable, a plain string for a secret, and a value outside a literal's values fail to typecheck; optional variables may be omitted:

```ts
import type { Manifest } from "@confect/core";
import * as Redacted from "effect/Redacted";
import manifest from "../backend/confect/_generated/manifest";

const values: Manifest.Values<typeof manifest> = {
  EMAIL_FROM: "noreply@example.edu",
  RESEND_API_KEY: Redacted.make(process.env.RESEND_API_KEY ?? ""),
  EMAIL_TRANSPORT: "resend",
};
```

`Manifest.Mounts<typeof manifest>` types the settings supplied under each mount's name. It includes only slots left open, with each slot's kind, optionality, and derived deployment variable in `manifest.mounts`. A mount with a required open slot must be supplied. Use [`Backend.mounts`](/guides/alchemy#supply-a-mounts-open-settings) to send those settings to their derived variables.

`http` lists `HttpApi` endpoints by owner, group, and endpoint name. An app's own endpoints use owner `app`. A mounted component's endpoints use its mount name, and nested owners include each placement, such as `relay/child`. Every leaf carries `method`, the full prefixed `path`, `owner`, `group`, `endpoint`, and the final manifest `digest`. Mounts without an HTTP prefix contribute no served routes. Generated documentation pages have no endpoint name and are omitted. A prefixed mount whose component ships no manifest contributes no routes, and codegen prints one note for that mount. Repeated owner, group and endpoint identities fail with `DuplicateRouteIdentity`; nested mounts under different parents have different owners.

`Manifest.RouteOf<typeof manifest>` is the union of these leaves. When a manifest keeps its digest as a literal, a leaf from a different digest fails that type. Infrastructure can read `manifest.http.bulkEmail.webhooks.resend` without importing backend modules.

`digest` covers every semantic field of the emitted manifest, including `sections`, plus the source fingerprint, mounted component digests, the `convex` version, the generator format and the `@confect/cli` version. Only the root digest and route-leaf digests are excluded. Object keys are sorted recursively, and source text uses LF line endings so CRLF inputs give the same digest. A dependency's exported slot change or child digest change also changes the host digest. Codegen writes the manifest before other validation and removes it when declaration generation fails.

Declared apps also receive `convex/confectHealth.ts`. Its internal query `confectHealth:digest` returns the final manifest digest. [`Confect.Backend`](/guides/alchemy#verify-the-deployed-manifest) uses that answer to check the live deployment after mount initialization. The generated query imports no backend code. The file is generated on every prepare and must not be edited or formatted. A component has no health query. The root group name `confectHealth` is reserved for this generated file; nested groups may use the name.

## Manifest sections

A library takes part in a backend's codegen through a manifest section. `App.make` declares the backend's sections, once, as `manifestSections`. Codegen reads them from there and from nowhere else, so a backend has a section whatever builders made its functions.

```ts confect/app.ts
import { App, type ManifestSection } from "@confect/core";
import env from "./env";

const tags: ManifestSection.ManifestSection<string> = {
  owner: "example/tags",
  format: 1,
  describe: ({ path }) => path,
};

export default App.make({
  env,
  manifestSections: [{ key: "tags", section: tags }],
});
```

Declared app codegen writes `sections: { tags: { format: 1, functions: { "notes:list": "notes:list" } } }` in `confect/_generated/manifest.ts`. `describe` runs on every registered function, whether a profile, a raw builder or a library's own builder made it. It receives the registered `path`, the `spec` and its group and function `middleware`. A backend with no functions still writes each declared section, with no functions. Callbacks run after specs load, including in `confect dev`, where spec edits update section data and the digest. Importing a spec never runs them. A component writes its descriptor without function sections, so it runs no `describe`, `summarize` or `check`; only `generate` and `verify` run for it.

Section data contributes to the digest, so declaring, removing or changing a section changes it, and so does a function joining or leaving a section. Each section declares a stable `owner` string. Codegen refuses a key `App.make` declares twice. Section names live under `sections` and may match built-in field names. Callbacks must preserve their inputs.

A function spec that carries `manifestSections` fails codegen with `InvalidDeclarationError`. The error names the spec file and the function, and says to declare the sections on `App.make` instead. A profile's `extend` throws at the call when its config carries a `manifest` option, and `.middleware` throws on a spec that carries `manifestSections`, with the same advice. An implementation that imports a `_generated` file no declared section writes fails with that file's name and the same advice, at the import.

### Generate a file from matched modules

An optional `generate` writes one file into `confect/_generated`.

```ts
const observe: ManifestSection.ManifestSection<null> = {
  owner: "example/observe",
  format: 1,
  describe: () => null,
  generate: {
    file: "observe.ts",
    match: (path) => /^[^/]+\/log\.ts$/.test(path),
    render: ({ modules }) => ({
      contents: modules
        .map(
          ({ relativePath }) =>
            `import "../${relativePath.replace(/\.ts$/, ".js")}";\n`,
        )
        .join(""),
      errors: [],
    }),
  },
};
```

`match` receives each `.ts` file under `confect/` outside `_generated`, as a path relative to `confect/` such as `billing/log.ts`. Codegen bundles every file it accepts and calls `render` with five lists, a lookup and three facts about the backend:

- `modules`: each accepted file's `relativePath` and its `exports`.
- `functions`: each function's `path`, such as `notes:list`, the `source` spec file that declares it, such as `notes.spec.ts`, its `visibility`: `"public"`, `"internal"`, or `"http"` for a route spec, its `group`, the key [Give each group its own module](#give-each-group-its-own-module) describes, such as `notes`, and its `spec`.
- `functionOf`: a lookup from a spec to the function whose `spec` is that very object.
- `mounts`: each mounted component's `name` and `definition`, the specifier of its definition directory. That is a package specifier such as `@convex-dev/workpool`, or a path relative to `confect/_generated` for a component in the same repository.
- `files`: every path `match` was offered, sorted, whether it accepted the file or not.
- `sections`: the key of every section `App.make` declares, in declared order, this section's own included. A component's sections get the keys its own `App.make` declares. Read it to import another section's file only when that section is declared, as in `sections.includes("tenancyRecord")`. A key names a section, not a file: a listed section may generate no file, or one named otherwise, so a section that imports another's file must know that section writes it.
- `target`: the backend being generated, `{ kind: "app" }` or `{ kind: "component", name }` with the name its `defineComponent` gives it, such as `ledger`.
- `deployment`: the kind of deployment codegen generates for, `"local"`, `"cloud"`, `"self-hosted"` or `"unknown"`. [Deployment kind](#deployment-kind) says how codegen decides it.
- `confectDirectory`: the absolute path of the backend's `confect/` folder, written with the platform's separators.

Codegen bundles the accepted files with every spec file in one build, so a module both reach is one instance. A spec an accepted file reaches through imports that build bundles, directly or through other modules, is the very object its function's `spec` is. Map a spec to its function with `functionOf`:

```ts
render: ({ modules, functionOf }) => {
  const named = modules.flatMap(({ exports }) =>
    (exports.included as ReadonlyArray<unknown>).map(
      (spec) => functionOf(spec).path,
    ),
  );
  return { contents: `export default ${JSON.stringify(named)};\n`, errors: [] };
},
```

A spec reached any other way is a different object. That happens when a module loads a spec file through `createRequire` or a `Module` instance's `require`, or through a package in `node_modules` that re-exports a spec from `confect/`. `functionOf` throws for such an object, and for a spec no group registers, naming the spec's function and these causes. Comparing with `spec` yourself finds no function for it, so use `functionOf` wherever a missing function would write a wrong entry.

A spec added to two groups, or to two leaves, is one object at two paths, and `functions` lists a function for each. `functionOf` throws for it rather than name one of them, and the message names the spec's function and every path, sorted: `functionOf got the spec of "notify", which is registered at 2 paths: "a/b:notify", "c:notify". A spec must be registered once for codegen to name its function.` Register a spec once.

`group` and `spec` are not enumerable, so serializing or spreading a function leaves them out, and a section that writes `functions` as JSON writes what it wrote before. `Object.getOwnPropertyNames` and `Reflect.ownKeys` still list them. `sections` is not enumerable either, so serializing or spreading the input, or reading it through `Object.keys` or `structuredClone`, leaves it out.

The accepted files run in the order of `files`, then the spec files. Each module runs its top level once, when the first file that imports it runs, so a module two accepted files import runs once rather than once for each of them. Packages Node loads from `node_modules` all load before any accepted file runs, so a package one accepted file imports cannot see state an earlier accepted file sets as it runs.

When the files cannot share one build, codegen bundles each accepted file on its own, and reading `spec` or calling `functionOf` throws why. That happens when a module the build reaches calls `import()` or `require()` with a path esbuild cannot read from the source, such as `import(new URL("../notes.spec.ts", import.meta.url).href)`, or with a path esbuild cannot resolve inside code that handles the failure. It also happens when `NODE_OPTIONS` sets export conditions, when the files fall under different `tsconfig.json` files, and when a package Node loads throws as it initializes. The section then fails with `generate failed: <message>` rather than miss a function.

`render` returns `{ contents, errors }`. Codegen writes `contents` into a `.ts` file under a two-line header that names the section and lists the accepted files. Each string in `errors` becomes an `InvalidManifestSectionError` under the section key. Every generating section renders before codegen fails with the first error, prints the rest from every section and writes no section file. A `match` or `render` that throws fails the same way, with the reason `generate failed: <message>`.

Every registration file in `_generated/registeredFunctions` and the declared HTTP router in `convex/http.ts` import each `.ts` section file before anything else, so the modules it imports load before any handler runs. Codegen still refuses a `convex/http.ts` that imports any other file, including one in `_generated` that no section wrote. It checks after it writes this run's section files, so a regeneration from an empty `_generated` accepts the router's imports of them. It removes a file no section claims only after rewriting these imports, so a failed run leaves no import of a removed file. Spec edits in `confect dev` render the file again, and a file that appears or goes updates every registration file. `confect dev` also regenerates when a file the section accepted, or a `confect/` file it imports, changes or is removed. Codegen records those files in `_generated/sectionInputs.json`, even when a section refuses or a module throws on load, so fixing the file regenerates. A file added to or removed from `confect/` triggers a full run, because every `render` sees `files`.

Codegen refuses a name codegen writes itself, such as `spec.ts`, `manifest.ts` or `sectionInputs.json`, a name that is not a `.ts`, `.json` or `.md` file directly in `_generated`, and a name two keys claim. It removes a file a section wrote once `App.make` no longer declares a section that claims it, and leaves other files in `_generated` alone. `generate` runs for a declared app and for a declared component, which `confect codegen --component-dir` generates. A component's registration files import the section file the same way, so its `confect/runtime.ts` needs no import of it. Without a section that generates, codegen output is unchanged.

A section can also generate data or a document that no code imports, such as `declarations.json` or `role-matrix.md`. A `.md` file gets the same header as HTML comments:

```md
<!-- Generated by `confect codegen` from the manifest section "matrix". Do not edit. -->
<!-- Sources: ["billing/log.ts"] -->
```

A `.json` file has no room for a header, so it holds exactly what `render` returned. Registered functions, `convex/http.ts` and `convex/crons.ts` import only `.ts` files, so codegen refuses `importedByFunctions: true` or `wrapsCrons: true` on a `.json` or `.md` file. Codegen records the `.json` and `.md` files the sections wrote in `_generated/sectionFiles.json`, with the SHA-256 digest of the bytes it wrote to each, as in `{"declarations.json":"sha256:…"}`. It also lists the modules [Give each group its own module](#give-each-group-its-own-module) describes, and exists only while it lists a file. The next run removes a file no section claims any more only while it still holds the bytes the record names. A file you edited stays, with a warning naming it, and codegen stops tracking it. A `.json` or `.md` file the record does not list is left alone. Codegen fails on a record that does not decode or that lists a name no section could claim, and names the record. Deleting it resets tracking, and the next run removes none of the files it listed. `confect dev` writes and removes these files as a full run does, and `sectionInputs.json` records the files their sections accepted, as it does for a `.ts` file.

### Import a file first

Set `importedFirst: true` on a section's `generate` when its file must load before anything else. Every registration file and `convex/http.ts` then import that file first, ahead of the other section files, so its module-load code runs before any function registers. A library binds a definition hook this way (see [Transform registered definitions](#transform-registered-definitions)). The file carries a second header line, `// Registered functions import this file first.`. Codegen refuses `importedFirst` on a second section, on a `.json` or `.md` file, and together with `importedByFunctions: false`. Without the option, the import order is unchanged.

### Give each group its own module

Registered functions import each `.ts` section file that does not set `importedByFunctions: false`, so everything such a file imports enters every function's bundle, and Convex loads it whenever it loads one of those functions. When part of the file serves only some groups, return `groups` from `render` as well: a function for each group that needs a module of its own, by the group's key. The key is the group's spec file's path in `confect/` without `.spec.ts`, with `/` between directories, such as `tasks/assignment`, and a spec file's nested groups share its module. Each function in `render`'s input carries its group's key as `group`, which is not enumerable, the same on every platform; `source` holds the spec file's path with the platform's separator, so take keys from `group`.

```ts
render: () => ({
  contents: "export {};\n",
  errors: [],
  groups: {
    "tasks/assignment": ({ importPath }) =>
      [
        `import { register } from ${JSON.stringify(importPath("inbox/registry.ts"))};`,
        `import { notify } from ${JSON.stringify(importPath("inbox/notify.ts"))};`,
        "register(notify);",
        "",
      ].join("\n"),
  },
}),
```

Here `inbox/registry.ts` exports `register` and `inbox/notify.ts` exports `notify`, both files of your own. Codegen calls each function once with `importPath` and writes the string it returns to the module's own file under the section's two-line header. `importPath` takes the path of an existing `.ts` file relative to `confect/`, with its extension, and returns the specifier the module imports it by, which ends in `.js`. Only that group's registration file imports the module, after the section files it imports, so what the module imports stays out of every other group's bundle. Set `importedByFunctions: false` too when the section's own file holds nothing every function needs.

The modules live in `_generated/sections/<file without .ts>/<group>.ts`, such as `_generated/sections/moduleFunctions/tasks/assignment.ts`, and `_generated/registeredFunctions/tasks/assignment.ts` gains one line, `import "../../sections/moduleFunctions/tasks/assignment.js";`. Don't write specifiers from this location by hand; get them from `importPath`. Codegen records each module, with a digest of its bytes, in `_generated/sectionFiles.json` after it writes the module, and drops a module from the record before it deletes the file. It overwrites a module at a path the record lists. At a path the record does not list, it writes a module only where nothing stands or where a file already holds the bytes it is about to write, and refuses a directory or any other file there, and anything but a directory above it. Once `render` no longer returns a module, codegen removes its file if it still holds the bytes the record names, with any directory that leaves empty; an edited file stays, with a warning. Codegen removes nothing in `_generated/sections` that the record does not list.

A run cut short between writing a module and recording it, or between dropping a module from the record and deleting it, leaves the module on disk unrecorded. A later run that writes the same bytes there records it again, so a retry succeeds after a run stopped between writes; one that would write other bytes refuses, and one that no longer returns the module leaves it in place. A run stopped in the middle of writing a module the record does not list leaves a partial file, which a later run that returns the module refuses by name.

On an incremental run, `confect dev` writes and removes the modules and writes every group's registration file, as a full run does.

Codegen refuses `groups` that is not a plain object of functions, a group that registers no Convex function, such as one that holds only routes or declares no function at all, a function that returns anything but a string, and `groups` on a `.json` or `.md` file, even an empty one. It refuses an `importPath` call with any other path: one that does not end in `.ts`, a declaration file such as `types.d.ts` or `styles.d.css.ts`, a file in `_generated`, since it takes a source file and not a generated one, an absolute path, a path outside `confect/`, a path that names no file, and a `.ts` file beside a `.js` file of the same name, such as `report.ts` beside `report.js`, because esbuild resolves the specifier to the `.js` file. `importPath` writes the same `.js` specifier codegen writes for its own imports, and it detects only a `.js` file of the same name, so another sibling the bundler prefers, such as `x.js.ts` beside `x.ts`, is not detected. `confect dev` does not regenerate when only a `.js` file under `confect/` is created, so it reports such a pair at its next regeneration. For a section that returns no `groups`, codegen writes no file under `_generated/sections` and no group entry in the record; the functions it receives also carry the non-enumerable `group`, which `Object.getOwnPropertyNames` lists.

### Wrap the deployment schema

Set `wrapsSchema: true` on a section's `generate`, and export `tables` from the file it renders, to change the tables Convex deploys. `tables` takes the backend's Confect tables by name and returns the Convex table definitions `defineSchema` gets in place of each table's own definition. It can add fields, index terms and whole tables:

```ts
// What the section's render returns as the contents of _generated/owners.ts
import { Table } from "@confect/server";
import { defineTable } from "convex/server";
import { v } from "convex/values";

export const tables = (confect) =>
  Object.fromEntries(
    Object.entries(confect).map(([name, table]) => [
      name,
      defineTable(
        v.object({
          ...Table.tableDefinition(table).validator.fields,
          owner: v.optional(v.string()),
        }),
      ).index("by_owner", ["owner"]),
    ]),
  );
```

This example assumes tables have no existing indexes and no `owner` field. It replaces their index definitions; a general wrapper must preserve ordinary, search and vector indexes.

A wrapper must call `Table.tableDefinition` on each table it is passed, as this one does, whether it returns that definition or builds another from it. `tableDefinition` runs the table's [deploy checks](/server/database/schema#deploy-checks), so a push refuses a table they refuse. A wrapper that skips it must run them itself with `Table.verifyDeploy` and throw the refusal; otherwise a push deploys a table its checks refuse, though codegen still refuses it.

`_generated/convexSchema.ts` then imports the file first and passes every table through it:

```ts
import { tables as $tables } from "./owners.js";
import { defineSchema as $defineSchema } from "convex/server";

import notes from "./tables/notes.js";

export default $defineSchema(
  $tables({
    notes,
  }),
);
```

`tables` runs when Convex loads the deployment schema. Registered functions import the section's file as they import any section file, unless it sets `importedByFunctions: false`, so keep the file's work inside `tables` and build no table definition as the file loads. The runtime `_generated/schema.ts`, which functions use, is unchanged, so a field `tables` adds is one the backend's own code does not see. A wrapper that throws stops the schema from loading, and one whose types don't fit `defineSchema` fails to type-check. Codegen refuses `wrapsSchema` on a second section and on a `.json` or `.md` file. Full runs and `confect dev` write the schema with this run's wrapper, so a section that starts or stops wrapping rewrites it. Without the option, the schema is unchanged.

### Summarize a section's data

An optional `summarize` replaces the section's `{ format, functions }` with data it builds. Added to the `observe` section above, it writes `sections: { observe: { format: 1, modules: ["billing/log.ts"] } }` into the manifest.

```ts
const observe: ManifestSection.ManifestSection<
  null,
  { readonly format: number; readonly modules: ReadonlyArray<string> }
> = {
  // owner, format, describe and generate as above
  summarize: ({ modules }) => ({
    format: 1,
    modules: modules.map(({ relativePath }) => relativePath),
  }),
};
```

`summarize` receives three inputs:

- `modules`: the files the section's `generate` accepted, with their exports, as `render` receives them. Without `generate` the list is empty.
- `functions`: each function's description, keyed by path.
- `sources`: the spec file that declares each of those functions, keyed by path and relative to `confect/`, such as `"inbox/inbox:list": "inbox/inbox.spec.ts"`.

The section's second type parameter types the result and `check`'s `next`. Codegen runs `summarize` after every `describe` and before `check` and the digest, so `check` judges what `summarize` returned and the digest covers it. The result must be JSON data, like a description, and carry the section's `format`. Otherwise codegen fails with `InvalidManifestSectionError` under the section key, and a `summarize` that throws fails with `summarize failed: <message>`. Spec edits in `confect dev` summarize again, and so does a change to a file the section accepted, because that change reruns codegen. Without `summarize`, the section's data and codegen output are unchanged.

### Description values must be JSON

Descriptions must contain only JSON data: plain objects, arrays, strings, finite numbers, booleans and `null`. JSON has no negative zero, so `-0` is written as `0`. BigInt, functions, undefined properties, non-finite numbers, cycles, symbol keys, and objects such as `Date`, `Map`, `Set` or class instances fail codegen with `InvalidDeclarationError`. Codegen never calls `toJSON` or a getter, so a value with either fails too, and so does a non-enumerable property or an array with properties besides its elements. The diagnostic names the section, function, declaring spec and JSON path, such as `$["nested"]["missing"]`. Empty property names remain in the path, for example `$[""]["missing"]`. Own `__proto__` properties are refused at their path because generated object literals cannot preserve them as data. A failing description removes the manifest through section failure cleanup.

### Check sections against previous output

An optional `check(next, previous)` returns `{ errors: string[], notes: string[] }`. `next` contains `format` and `functions`, or what `summarize` returned; `previous` is the old section as `unknown`, or `undefined` when no usable previous section exists. Validate its format before comparing. Section history uses own keys only, including a section named like `constructor` or `__proto__`. A previous manifest that cannot be decoded supplies no sections and prints one warning that history starts fresh. A missing previous file supplies no sections without a warning. Every note prints and any error fails codegen. Check errors and a thrown check fail with `InvalidManifestSectionError`, headed by the section key; errors from every failing section are reported. A `describe` that throws fails with its own message under the section, the function and the declaring spec. Only a failing section step removes the manifest; unrelated spec or implementation failures retain the manifest and its previous sections. The early declaration write carries previous sections forward while applying declaration edits. Files whose content is unchanged are not written or logged as modified.

A section `App.make` no longer declares leaves the manifest with no note, because no callback remains to run.

### Verify the backend after generation

An optional `generate.verify` checks the backend once every `_generated` file exists. Its files may import any generated file, including the section's own, which a `render` input cannot.

```ts
const doors: ManifestSection.ManifestSection<null> = {
  owner: "example/doors",
  format: 1,
  describe: () => null,
  generate: {
    file: "doors.ts",
    match: () => false,
    render: () => ({ contents: "export {};\n", errors: [] }),
    verify: {
      match: (path) => path.endsWith("door.ts"),
      check: ({ modules, mounts }) =>
        mounts
          .filter(
            ({ name }) =>
              !modules.some(({ exports }) => exports.mount === name),
          )
          .map(({ name }) => `No door owns the mount ${name}.`),
    },
  },
};
```

Codegen runs `verify` last, after it validates every implementation and writes every generated file, in full runs and on spec edits in `confect dev`. `verify.match` receives the same paths `generate.match` does. Codegen bundles each file it accepts the way it bundles `confect/app.ts`, so an import of a component's `convex.config` resolves. Then it calls `check` with seven inputs:

- `modules`: each accepted file's `relativePath` and its `exports`.
- `functions`: each function with its `path`, `source`, `visibility` and `spec`, as `render` receives them. Codegen bundles the files `verify.match` accepts with every spec file in one build, so a spec an accepted file reaches through imports that build bundles is the very object its function's `spec` is.
- `functionOf`: the lookup from a spec to its function, as `render` receives it.
- `mounts`: each mounted component's `name` and `definition`, as `render` receives them.
- `target`: the backend being generated, as `render` receives it.
- `deployment`: the kind of deployment codegen generates for, as `render` receives it.
- `guard`: the name the guard in `http.ts` was made with, such as `"none"`, or `undefined` when `http.ts` declares none.

A framework that admits only its own guard refuses any other name here, and a section can refuse route specs in a component by reading `target` with each function's `visibility`.

Each string `check` returns becomes an `InvalidManifestSectionError` under the section key. Every verifying section checks before codegen fails with the first error and prints the rest. A `match` or `check` that throws fails the same way, with the reason `verify failed: <message>`. Codegen records the files `verify` loaded and their `confect/` imports in `_generated/verifyInputs.json`, so `confect dev` checks again when one changes, an implementation or spec file included. Without a section that verifies, codegen output is unchanged.

### Refuse a push

`verify` runs only when codegen does. A push that skips codegen, or a `convex dev` watcher that pushes an edit before codegen reruns, deploys whatever source it bundled. To refuse such a push too, register a check for the backend at runtime with `PushCheck.register` from `@confect/server/PushCheck`, keyed by the default export of its generated `_generated/schema` module. Nothing in the generated files changes.

```ts
// confect/door.ts, which every implementation of the backend imports
import * as PushCheck from "@confect/server/PushCheck";
import schema from "./_generated/schema";

PushCheck.register(
  schema,
  PushCheck.make("doors", () => refusals()),
);
```

The check returns its refusals as strings, and none when the source passes. Registering runs nothing. Every query, mutation and action Confect registers for the backend, a group's raw Convex functions included, runs the registered checks from its `exportArgs`, and the router `HttpRouter.make` builds runs them from its `getRoutes`. Convex calls both while it analyzes a push and never while it serves a call. A refusal fails the push, and the deployment keeps serving the last push that succeeded. A check runs at most once per check value in each loaded copy of `@confect/server`, so a call pays nothing.

Convex evaluates each entry's own module graph when it analyzes it, so an entry runs only the checks its graph registers. Register from a module every entry of the backend imports, such as a provider its implementations use. A backend with neither a function nor a router runs no check at a push, and neither does a backend whose entries never reach the registration; give `Preflight.run` the schema to refuse the first.

Convex's message for a refused isolate or component function names no function, so the refusal names the check and the function Convex was analyzing, and each refusal should name the declaration it refuses:

```
Hit an error while pushing:
Uncaught PushRefused: Push check "doors" refused the source while Convex analyzed list: no door owns the mount email
```

A `"use node"` action's refusal reads `Failed to analyze tasks/node.js: Push check "doors" refused …`. Convex discards a throw from `getRoutes`, so a refusing router returns one route whose method is the refusal, which Convex prints inside its own error: ``The `getRoutes()` method of Router did not return the expected type. … ('Push check "doors" refused the source while Convex analyzed http: …' is not not a routable method …)``.

`exportArgs` is marked `@internal` in Convex, which does not promise to keep calling it during analysis. Pin Convex exactly and repeat the push contract test on each upgrade. A test backend never pushes, so `@confect/test`'s layers run a backend's push checks as they build it, before any call, an HTTP request included, and die with `PushRefused` on a refusal. See [Push checks](/guides/testing#push-checks) in the testing guide. For a backend built another way, such as `convexTest` directly, run `Preflight.run(modules, { schema })` from `@confect/test` before its first call.

### Transform registered definitions

A library can change each Convex function definition Confect registers, before Convex sees it, with `RegisteredConvexFunction.bindDefinitionHook` from `@confect/server`. The hook receives the function's visibility, `"public"` or `"internal"`, and its Convex definition, `{ args, returns, handler }`, and returns the definition to register in its place. This hook adds an optional `note` argument to internal functions whose validator is an object and has no `note` of its own, and removes it before the handler runs. A function that already takes a `note` keeps its validator and receives its own value:

```ts
import { RegisteredConvexFunction } from "@confect/server";
import { asObjectValidator, v } from "convex/values";

RegisteredConvexFunction.bindDefinitionHook((visibility, definition) => {
  if (visibility !== "internal") return definition;
  // The object validator to extend, or none: the function has no object
  // validator, or already takes a `note` of its own.
  const reservable = () => {
    const args = definition.args;
    const object = args === undefined ? undefined : asObjectValidator(args);
    return object?.kind === "object" && !Object.hasOwn(object.fields, "note")
      ? object
      : undefined;
  };
  const hooked = {
    handler: (ctx, args) => {
      if (reservable() === undefined) return definition.handler(ctx, args);
      const { note, ...rest } = args;
      return definition.handler(ctx, rest);
    },
  };
  Object.defineProperty(hooked, "args", {
    enumerable: true,
    get: () => {
      const object = reservable();
      return object === undefined
        ? definition.args
        : v.object({ ...object.fields, note: v.optional(v.string()) });
    },
  });
  Object.defineProperty(hooked, "returns", {
    enumerable: true,
    get: () => definition.returns,
  });
  return hooked;
});
```

The hook sees every query, mutation and action that a generated registration or `RegisteredConvexFunction.register` registers from a prepared definition, and every Node action. It never sees a raw Convex function a group carries, which Convex already registered. Push checks still run, since Confect guards the function Convex returns for the hooked definition. With no hook bound, every definition registers unchanged.

The hook is a trusted extension point. It can replace any function's validator and handler, so bind only code you trust as you trust the backend's own. Confect's push checks run on the function Convex registers, but they do not prove that a replacement keeps the original's meaning.

`args` and `returns` are lazy getters, and reading either compiles the function's schemas, which Confect otherwise does only when Convex reads the validators. Define your own as getters, as above, so a function's module load builds no schema.

A hook binds once, before any function registers, so it sees every definition. Bind it from the file of a section that sets [`importedFirst`](#import-a-file-first). A second bind, of any hook, throws `RegisteredConvexFunction.DefinitionHookRefused` with reason `AlreadyBound`, and a bind after a function has registered throws it with reason `FunctionRegistered`, since that function registered without the hook. A hook that throws stops the module registering the function from loading. The hook applies to the copy of `@confect/server` it was bound on, which is the copy the generated registrations import when the library and the backend resolve the same package.

### Deployment kind

`confect codegen --deployment-kind <local|cloud|self-hosted>` and the same flag on `confect dev` tell codegen the kind. Without the flag, codegen reads `CONFECT_DEPLOYMENT_KIND` from its environment, never from a file, and an empty value counts as unset. A flag and a variable that disagree give `"unknown"`, and so does a `CONFECT_DEPLOYMENT_KIND` other than `local`, `cloud` or `self-hosted`. `Confect.Backend` sets `CONFECT_DEPLOYMENT_KIND` to `cloud`, or `local` under the local providers, for its `prepare` command, so a wrapper such as `pnpm exec confect codegen` passes it on.

With neither, codegen reads the variables the Convex CLI selects a deployment with, from the environment, then `.env.local`, then `.env` in the project root. As in the Convex CLI, a variable set at one layer hides the layers below it even when its value is empty, and an empty value then counts as unset:

| Variables                                                                         | Kind            |
| --------------------------------------------------------------------------------- | --------------- |
| `CONVEX_DEPLOYMENT` naming an `anonymous-` deployment, or starting `local:`       | `"local"`       |
| `CONVEX_DEPLOYMENT` starting `dev:`, `prod:` or `preview:`                        | `"cloud"`       |
| `CONVEX_DEPLOY_KEY`, or else `CONVEX_DEPLOYMENT_TOKEN`, holding a key with a `\|` | `"cloud"`       |
| Both `CONVEX_SELF_HOSTED_URL` and `CONVEX_SELF_HOSTED_ADMIN_KEY`                  | `"self-hosted"` |

Anything else is `"unknown"`: no variables, a value the Convex CLI would refuse or resolve through its servers, one self-hosted variable without the other, an anonymous deployment while `CONVEX_ALLOW_ANONYMOUS` is `false`, or two groups that name different kinds. A section that relaxes a rule only on a backend you run yourself should treat `"unknown"` as hosted. The kind is what codegen can see when it runs. A later push that picks its target another way, such as `convex deploy --prod` or `--env-file`, does not change it. `confect dev` decides the kind once when it starts.

## Development

Run `confect dev` alongside `convex dev`. Confect watches declaration inputs and their project imports, regenerates the Convex config, auth, HTTP entry point and manifest, and leaves deployment to Convex. Run component watchers separately with `confect dev --component-dir components/counter/convex` when developing a local component.

`confect dev --coalesce-ms <milliseconds>` sets the quiet period after a save, defaults to 50 ms, and accepts integers from 0 to 5000, capped by the 5 s maximum wait.

`confect dev --deployment-kind <kind>` sets the [deployment kind](#deployment-kind) the sections receive.

## Adopting the declaration

1. Write `confect/env.ts` and `confect/app.ts` from your current `convex/convex.config.ts`.
2. Move a hand-written `confect/auth.ts` into `Auth.make(app, { providers })`, and `confect/http.ts` into `Http.make`.
3. Delete `convex/convex.config.ts`, and `convex/auth.config.ts` if you wrote it yourself.
4. Run `confect codegen`.

Codegen refuses to overwrite a `convex.config.ts` or `auth.config.ts` it did not write, and prints which declaration file now owns it. To stop using the declaration, delete `confect/app.ts` and write `convex/convex.config.ts` yourself again.
