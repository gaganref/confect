description: "Declare a backend's env, mounted components, auth providers and HTTP API in confect/, and let codegen write convex.config.ts, auth.config.ts and a manifest."

A backend declaration describes your Convex backend in four files beside your functions. `confect codegen` and `confect dev` then write `convex/convex.config.ts`, `convex/auth.config.ts`, `convex/http.ts` and `confect/_generated/manifest.ts` from it, so the env your handlers read, the env Convex validates, the env each mounted component receives and the env your infrastructure supplies all come from one place.

After upgrading to the fork based on upstream 10.3.1, run `confect codegen` again. The generator output changed; do not keep files emitted by the previous generator.

The declaration is opt-in. It applies when `confect/app.ts` exists. Without that file, you write `convex/convex.config.ts` yourself and `confect/auth.ts` and `confect/http.ts` keep their [existing forms](/concepts/project-structure).

| File              | Holds                                | Codegen writes                                           |
| ----------------- | ------------------------------------ | -------------------------------------------------------- |
| `confect/env.ts`  | `Env.make(name, { ... })`            | The `env` of `convex/convex.config.ts`, and the manifest |
| `confect/app.ts`  | `App.make({ env, mounts })`          | `convex/convex.config.ts`, and the manifest              |
| `confect/auth.ts` | `Auth.make(app, { providers })`      | `convex/auth.config.ts`                                  |
| `confect/http.ts` | `Http.make({ api, handlers, docs })` | `convex/http.ts`                                         |

## `env.ts`

Declare every environment variable the backend reads, once, with its backend's name:

```ts confect/env.ts
import { Env } from "@confect/core";

export default Env.make("tenant", {
  EMAIL_FROM: Env.string(),
  RESEND_API_KEY: Env.secret(),
  EMAIL_TRANSPORT: Env.literals(["resend", "log"]),
  PLATFORM_URL: Env.optional(Env.string()),
});
```

Each entry is an Effect `Config`. Import the env in a handler and yield an entry to read it:

```ts confect/emails.impl.ts
import * as Effect from "effect/Effect";
import env from "./env";

export const configuration = Effect.gen(function* () {
  const from = yield* env.EMAIL_FROM; // string
  const key = yield* env.RESEND_API_KEY; // Redacted<string>
  const transport = yield* env.EMAIL_TRANSPORT; // "resend" | "log"
  const platform = yield* env.PLATFORM_URL; // Option<string>
  return { from, key, transport, platform };
});
```

| Constructor           | Handler reads       | Convex validator               |
| --------------------- | ------------------- | ------------------------------ |
| `Env.string()`        | `string`            | `v.string()`                   |
| `Env.secret()`        | `Redacted<string>`  | `v.string()`                   |
| `Env.literals([...])` | one of the literals | `v.union(v.literal(...), ...)` |
| `Env.optional(entry)` | `Option<...>`       | `v.optional(...)`              |

The name is the backend's identity. An entry from one backend's env cannot be bound in another backend's mounts. For a [Confect-authored component](/server/components), the name is also the component's Convex name.

Reads resolve through Confect's [Convex-aware `ConfigProvider`](/server/environment-variables), as any other `Config` does. Import `env.ts` from handlers, never `app.ts`: `app.ts` imports component definitions, which load only in Convex's config analysis.

## `app.ts`

List the `convex.config` definitions of the Convex components the backend mounts, then its mounts. Each mount is declared in its own `confect/<mount>.ts` with [`Mount.make`](/server/components#reach-a-mounts-client), which takes the component's descriptor and the env each mount receives:

```ts confect/app.ts
import { App } from "@confect/core";
import workpool from "@convex-dev/workpool/convex.config.js";
import email from "@acme/email/convex.config.js";
import { BulkEmail } from "./bulkEmail";
import { ImportsPool } from "./importsPool";
import env from "./env";

export default App.make({
  env,
  components: [email, workpool],
  mounts: [BulkEmail, ImportsPool],
});
```

```ts confect/bulkEmail.ts
import { Mount } from "@confect/core";
import Email from "@acme/email/client";
import env from "./env";

export const BulkEmail = Mount.make(Email, {
  name: "bulkEmail",
  httpPrefix: "/bulk-email",
  env: {
    FROM: env.EMAIL_FROM,
    RESEND_API_KEY: env.RESEND_API_KEY,
    TRANSPORT: env.EMAIL_TRANSPORT,
  },
});
```

Set `requiresMiddleware` in `App.make` to require middleware on every registered function, including internal functions. Requirements are matched by middleware key. Codegen fails once with every uncovered function's group path and name. Generated registration also applies `GroupImpl.finalize({ required, groupPath })` when its layer builds. Attach middleware to each function or its own group. Raw Convex functions cannot satisfy this requirement. Mounted backends declare their own requirements; HTTP middleware is separate.

```ts
import { Policy, Trace } from "./middleware";
export default App.make({ env, requiresMiddleware: [Policy, Trace] });
```

Each mount names itself. Codegen pairs it with the listed definition whose `defineComponent` name is its component's name, and writes one `app.use` per mount in list order. It fails, naming the mount or definition, when a mount's component has no listed definition, when a listed definition has no mount, when two mounts share a name, and when two listed definitions share a `defineComponent` name. `Mount.make` types `env` against the descriptor's env slots. These fail to typecheck:

- leaving out a binding the component requires
- binding an optional entry to a required slot
- binding a value outside a literal slot's values
- binding a slot the component does not declare
- binding an entry from another backend's env (reported at `App.make`)

A binding is an entry of your env, or a constant string. `httpPrefix` reserves the mounted Convex component's routes.

The [generated test registry](/guides/testing) discovers a mounted Convex component's test kit at `<package>/testing`, then `<package>/test`, unless the component's descriptor names one with `testing`. Mounts do not accept a `testing` option.

Codegen writes the matching Convex definition:

```ts convex/convex.config.ts
// Generated by `confect codegen` from confect/app.ts. Do not edit.
import { defineApp } from "convex/server";
import { v } from "convex/values";
import workpool from "@convex-dev/workpool/convex.config.js";
import email from "@acme/email/convex.config.js";

const app = defineApp({
  env: {
    EMAIL_FROM: v.string(),
    RESEND_API_KEY: v.string(),
    EMAIL_TRANSPORT: v.union(v.literal("resend"), v.literal("log")),
    PLATFORM_URL: v.optional(v.string()),
  },
});

app.use(email, {
  name: "bulkEmail",
  httpPrefix: "/bulk-email",
  env: {
    FROM: app.env.EMAIL_FROM,
    RESEND_API_KEY: app.env.RESEND_API_KEY,
    TRANSPORT: app.env.EMAIL_TRANSPORT,
  },
});

app.use(workpool, {
  name: "importsPool",
});

export default app;
```

A Confect-authored component declares itself with `App.make({ kind: "component", env, components, mounts })`, with `env.ts` and `app.ts` in its own `confect/` directory. `confect codegen --component-dir` writes its `defineComponent(name, { env })`. The kind defaults to `"app"`; codegen rejects a declaration whose kind differs from the target directory. Components can mount other components, but `Auth.make` accepts only app declarations.

## `auth.ts`

Declare the identity providers whose tokens the backend accepts. This is Convex's own [provider list](https://docs.convex.dev/auth/advanced/custom-auth). Use `Auth.siteUrl` for the deployment's site URL and `Auth.cloudUrl` for its cloud URL. `domain`, `issuer`, `jwks` and `applicationID` also accept required `Env.string()` or `Env.literals(...)` entries from this backend:

```ts confect/auth.ts
import { Auth } from "@confect/core";
import app from "./app";
import { BulkEmail } from "./bulkEmail";

export default Auth.make(app, {
  providers: [
    { domain: "https://login.example.edu", applicationID: "tenant" },
    {
      type: "customJwt",
      applicationID: "tenant",
      issuer: Auth.siteUrl(),
      jwks: Auth.siteUrl(BulkEmail, "/.well-known/jwks.json"),
      algorithm: "RS256",
    },
  ],
});
```

Codegen writes `convex/auth.config.ts` with deployment URLs as `process.env.CONVEX_SITE_URL` or `process.env.CONVEX_CLOUD_URL` expressions and env entries as `process.env["KEY"]!`. It never reads env values during generation. Optional entries and secrets are rejected. The output uses `satisfies AuthConfig`. Components cannot declare `auth.ts`.

For deployment-signed JWTs, use `Auth.cloudUrl("/components/auth")` as the issuer, `Auth.cloudUrl("/.well-known/jwks.json")` as the JWKS, and `"ES256"` as the algorithm. `Auth.siteUrl()` can supply the receiving deployment's `applicationID`; a session provider can keep `"convex"`. Cloud URL paths are explicit because component issuer paths differ from HTTP mount prefixes.

### Runtime provider data

An optional `family` and `name` on each provider are application-defined strings.
Codegen omits them from Convex's auth config and writes
`confect/_generated/auth.providers.ts` for handlers:

```ts
import { providers } from "./_generated/auth.providers";
```

Each entry has `issuer` (the provider's `issuer` or `domain`), `audience` when
`applicationID` is present, and the declared `family` and `name`. URL and env
expressions resolve in the deployment. The generated module imports nothing, so
handlers can classify verified identities without importing `auth.ts`, `app.ts`,
or component definitions. Existing providers need no metadata. Removing `auth.ts`
removes both generated auth files.

## `http.ts`

Declare the backend's own `HttpApi` and its handlers. `docs` is optional and serves a Scalar page for the api at that path:

```ts confect/http.ts
import { Http } from "@confect/core";
import { TenantApi, TenantHandlers } from "./api";

export default Http.make({
  api: TenantApi,
  handlers: TenantHandlers,
  docs: "/docs",
});
```

Every route is an `HttpApi` endpoint. Codegen writes `convex/http.ts`, which serves it through [`HttpRouter`](/server/http-api):

```ts convex/http.ts
// Generated by `confect codegen` from confect/http.ts. Do not edit.
import { HttpRouter } from "@confect/server";
import schema from "../confect/_generated/schema";
import http from "../confect/http";

export default HttpRouter.forSchema(schema)(http.routes, { api: http.api });
```

The schema supplies the backend's capabilities; `{ api }` supplies endpoint labels for Convex logs and the dashboard. Mounted components serve their own routes under their prefixes; your middleware does not run in front of them.

Codegen fails when an app route or the docs page is at or under a mount's prefix, because Convex accepts such a route and lets it silently shadow the component's. It also fails when two of the backend's own routes share a method and path, or when two mount prefixes overlap. Prefix checks run even without `http.ts`. Each Convex component checks its own routes during codegen.

## The manifest

`confect/_generated/manifest.ts` is plain data with no imports. Infrastructure that deploys the backend reads it instead of backend code:

```ts confect/_generated/manifest.ts
export default {
  name: "tenant",
  env: {
    EMAIL_FROM: { kind: "string", optional: false },
    RESEND_API_KEY: { kind: "secret", optional: false },
    EMAIL_TRANSPORT: {
      kind: "literals",
      values: ["resend", "log"],
      optional: false,
    },
    PLATFORM_URL: { kind: "string", optional: true },
  },
  http: { mounts: { bulkEmail: "/bulk-email" } },
  digest: "sha256:…",
} as const;
```

`Manifest.Values` types the values a deployment supplies. A missing required variable, a plain string for a secret, and a value outside a literal's values fail to typecheck; optional variables may be omitted:

```ts
import type { Manifest } from "@confect/core";
import * as Redacted from "effect/Redacted";
import manifest from "../backend/confect/_generated/manifest";

const values: Manifest.Values<typeof manifest> = {
  EMAIL_FROM: "noreply@example.edu",
  RESEND_API_KEY: Redacted.make(process.env.RESEND_API_KEY ?? ""),
  EMAIL_TRANSPORT: "resend",
};
```

`digest` changes whenever a file that `env.ts`, `app.ts` or `auth.ts` imports from your project changes, or the `convex` version or generator format does. Codegen writes the manifest before it validates anything else, and removes it when the declaration fails, so a stale manifest never outlives the declaration it came from.

## Manifest sections

A library takes part in a backend's codegen through a manifest section. `App.make` declares the backend's sections, once, as `manifestSections`. Codegen reads them from there and from nowhere else, so a backend has a section whatever builders made its functions.

```ts confect/app.ts
import { App, type ManifestSection } from "@confect/core";
import env from "./env";

const tags: ManifestSection.ManifestSection<string> = {
  owner: "example/tags",
  format: 1,
  describe: ({ path }) => path,
};

export default App.make({
  env,
  manifestSections: [{ key: "tags", section: tags }],
});
```

Declared app codegen writes `tags: { format: 1, functions: { "notes:list": "notes:list" } }` in `confect/_generated/manifest.ts`. `describe` runs on every registered function, whether a profile, a raw builder or a library's own builder made it. It receives the registered `path`, the `spec` and its group and function `middleware`. A backend with no functions still writes each declared section, with no functions. Callbacks run after specs load, including in `confect dev`, where spec edits update section data and the digest. Importing a spec never runs them. A component has no manifest, so it runs no `describe`, `summarize` or `check`; only `generate` and `verify` run for it.

Section data contributes to the digest, so declaring, removing or changing a section changes it, and so does a function joining or leaving a section. Each section declares a stable `owner` string. Codegen refuses a key `App.make` declares twice and the keys `name`, `env`, `http`, `digest`, `__proto__`, `constructor` and `prototype`. Callbacks must preserve their inputs.

A function spec that carries `manifestSections` fails codegen with `InvalidDeclarationError`. The error names the spec file and the function, and says to declare the sections on `App.make` instead. A profile's `extend` throws at the call when its config carries a `manifest` option, and `.middleware` throws on a spec that carries `manifestSections`, with the same advice. An implementation that imports a `_generated` file no declared section writes fails with that file's name and the same advice, at the import.

### Generate a file from matched modules

An optional `generate` writes one file into `confect/_generated`.

```ts
const observe: ManifestSection.ManifestSection<null> = {
  owner: "example/observe",
  format: 1,
  describe: () => null,
  generate: {
    file: "observe.ts",
    match: (path) => /^[^/]+\/log\.ts$/.test(path),
    render: ({ modules }) => ({
      contents: modules
        .map(
          ({ relativePath }) =>
            `import "../${relativePath.replace(/\.ts$/, ".js")}";\n`,
        )
        .join(""),
      errors: [],
    }),
  },
};
```

`match` receives each `.ts` file under `confect/` outside `_generated`, as a path relative to `confect/` such as `billing/log.ts`. Codegen bundles every file it accepts and calls `render` with four lists and two facts about the backend:

- `modules`: each accepted file's `relativePath` and its `exports`.
- `functions`: each registered function's `path`, such as `notes:list`, and the `source` spec file that declares it, such as `notes.spec.ts`.
- `mounts`: each mounted component's `name` and `definition`, the specifier of its definition directory. That is a package specifier such as `@convex-dev/workpool`, or a path relative to `confect/_generated` for a component in the same repository.
- `files`: every path `match` was offered, sorted, whether it accepted the file or not.
- `target`: the backend being generated, `{ kind: "app" }` or `{ kind: "component", name }` with the name its `defineComponent` gives it, such as `ledger`.
- `confectDirectory`: the absolute path of the backend's `confect/` folder, written with the platform's separators.

`render` returns `{ contents, errors }`. Codegen writes `contents` under a two-line header that names the section and lists the accepted files. Each string in `errors` becomes an `InvalidManifestSectionError` under the section key. Every generating section renders before codegen fails with the first error, prints the rest from every section and writes no section file. A `match` or `render` that throws fails the same way, with the reason `generate failed: <message>`.

Every registration file in `_generated/registeredFunctions` and the declared HTTP router in `convex/http.ts` import each section file before anything else, so the modules it imports load before any handler runs. Codegen still refuses a `convex/http.ts` that imports any other file, including one in `_generated` that no section wrote. It checks after it writes this run's section files, so a regeneration from an empty `_generated` accepts the router's imports of them. It removes a file no section claims only after rewriting these imports, so a failed run leaves no import of a removed file. Spec edits in `confect dev` render the file again, and a file that appears or goes updates every registration file. `confect dev` also regenerates when a file the section accepted, or a `confect/` file it imports, changes or is removed. Codegen records those files in `_generated/sectionInputs.json`, even when a section refuses or a module throws on load, so fixing the file regenerates. A file added to or removed from `confect/` triggers a full run, because every `render` sees `files`.

Codegen refuses a name codegen writes itself, such as `spec.ts` or `manifest.ts`, a name that is not a `.ts` file directly in `_generated`, and a name two keys claim. It removes a file a section wrote once `App.make` no longer declares a section that claims it, and leaves other files in `_generated` alone. `generate` runs for a declared app and for a declared component, which `confect codegen --component-dir` generates. A component's registration files import the section file the same way, so its `confect/runtime.ts` needs no import of it. Without a section that generates, codegen output is unchanged.

### Summarize a section's data

An optional `summarize` replaces the section's `{ format, functions }` with data it builds. Added to the `observe` section above, it writes `observe: { format: 1, modules: ["billing/log.ts"] }` into the manifest.

```ts
const observe: ManifestSection.ManifestSection<
  null,
  { readonly format: number; readonly modules: ReadonlyArray<string> }
> = {
  // owner, format, describe and generate as above
  summarize: ({ modules }) => ({
    format: 1,
    modules: modules.map(({ relativePath }) => relativePath),
  }),
};
```

`summarize` receives three inputs:

- `modules`: the files the section's `generate` accepted, with their exports, as `render` receives them. Without `generate` the list is empty.
- `functions`: each function's description, keyed by path.
- `sources`: the spec file that declares each of those functions, keyed by path and relative to `confect/`, such as `"inbox/inbox:list": "inbox/inbox.spec.ts"`.

The section's second type parameter types the result and `check`'s `next`. Codegen runs `summarize` after every `describe` and before `check` and the digest, so `check` judges what `summarize` returned and the digest covers it. The result must be JSON data, like a description, and carry the section's `format`. Otherwise codegen fails with `InvalidManifestSectionError` under the section key, and a `summarize` that throws fails with `summarize failed: <message>`. Spec edits in `confect dev` summarize again, and so does a change to a file the section accepted, because that change reruns codegen. Without `summarize`, the section's data and codegen output are unchanged.

### Description values must be JSON

Descriptions must contain only JSON data: plain objects, arrays, strings, finite numbers, booleans and `null`. JSON has no negative zero, so `-0` is written as `0`. BigInt, functions, undefined properties, non-finite numbers, cycles, symbol keys, and objects such as `Date`, `Map`, `Set` or class instances fail codegen with `InvalidDeclarationError`. Codegen never calls `toJSON` or a getter, so a value with either fails too, and so does a non-enumerable property or an array with properties besides its elements. The diagnostic names the section, function, declaring spec and JSON path, such as `$["nested"]["missing"]`. Empty property names remain in the path, for example `$[""]["missing"]`. Own `__proto__` properties are refused at their path because generated object literals cannot preserve them as data. A failing description removes the manifest through section failure cleanup.

### Check sections against previous output

An optional `check(next, previous)` returns `{ errors: string[], notes: string[] }`. `next` contains `format` and `functions`, or what `summarize` returned; `previous` is the old section as `unknown`, or `undefined` when no usable previous section exists. Validate its format before comparing. An unreadable, empty, missing-default or null previous manifest supplies no sections. Every note prints and any error fails codegen. Check errors and a thrown check fail with `InvalidManifestSectionError`, headed by the section key; errors from every failing section are reported. A `describe` that throws fails with its own message under the section, the function and the declaring spec. Only a failing section step removes the manifest; unrelated spec or implementation failures retain the manifest and its previous sections. The early declaration write carries previous sections forward while applying declaration edits. Files whose content is unchanged are not written or logged as modified.

A section `App.make` no longer declares leaves the manifest with no note, because no callback remains to run.

### Verify the backend after generation

An optional `generate.verify` checks the backend once every `_generated` file exists. Its files may import any generated file, including the section's own, which a `render` input cannot.

```ts
const doors: ManifestSection.ManifestSection<null> = {
  owner: "example/doors",
  format: 1,
  describe: () => null,
  generate: {
    file: "doors.ts",
    match: () => false,
    render: () => ({ contents: "export {};\n", errors: [] }),
    verify: {
      match: (path) => path.endsWith("door.ts"),
      check: ({ modules, mounts }) =>
        mounts
          .filter(
            ({ name }) =>
              !modules.some(({ exports }) => exports.mount === name),
          )
          .map(({ name }) => `No door owns the mount ${name}.`),
    },
  },
};
```

Codegen runs `verify` last, after it validates every implementation and writes every generated file, in full runs and on spec edits in `confect dev`. `verify.match` receives the same paths `generate.match` does. Codegen bundles each file it accepts the way it bundles `confect/app.ts`, so an import of a component's `convex.config` resolves. Then it calls `check` with three inputs:

- `modules`: each accepted file's `relativePath` and its `exports`.
- `mounts`: each mounted component's `name` and `definition`, as `render` receives them.
- `target`: the backend being generated, as `render` receives it.

Each string `check` returns becomes an `InvalidManifestSectionError` under the section key. Every verifying section checks before codegen fails with the first error and prints the rest. A `match` or `check` that throws fails the same way, with the reason `verify failed: <message>`. Codegen records the files `verify` loaded and their `confect/` imports in `_generated/verifyInputs.json`, so `confect dev` checks again when one changes, an implementation or spec file included. Without a section that verifies, codegen output is unchanged.

## Development

Run `confect dev` alongside `convex dev`. Confect watches declaration inputs and their project imports, regenerates the Convex config, auth, HTTP entry point and manifest, and leaves deployment to Convex. Run component watchers separately with `confect dev --component-dir components/counter/convex` when developing a local component.

`confect dev --coalesce-ms <milliseconds>` sets the quiet period after a save, defaults to 50 ms, and accepts integers from 0 to 5000, capped by the 5 s maximum wait.

## Adopting the declaration

1. Write `confect/env.ts` and `confect/app.ts` from your current `convex/convex.config.ts`.
2. Move a hand-written `confect/auth.ts` into `Auth.make(app, { providers })`, and `confect/http.ts` into `Http.make`.
3. Delete `convex/convex.config.ts`, and `convex/auth.config.ts` if you wrote it yourself.
4. Run `confect codegen`.

Codegen refuses to overwrite a `convex.config.ts` or `auth.config.ts` it did not write, and prints which declaration file now owns it. To stop using the declaration, delete `confect/app.ts` and write `convex/convex.config.ts` yourself again.
