Your database schema lives in `confect/tables/`: one file per table, each default-exporting a `Table.make(...)` value, where the **filename is the table name** (`confect/tables/notes.ts` defines a table called `notes`). The Confect CLI's codegen combines these files into a single schema behind the scenes—and generates the per-table helpers your code imports—so you never assemble or edit a schema definition by hand. (For the full layout of what codegen emits, see [Project Structure](/concepts/project-structure).)

Each table is defined with `Table.make`, which takes a callback returning the table's fields. The callback runs lazily—only the first time the table's `Fields` or `Doc` is accessed—so a function that never touches a table pays no schema-construction cost for it at cold start. Indexes are defined on tables the same way as in the base Convex APIs. Cross-table `Id` references are constructed with the codegen-emitted `Id` helper from `confect/_generated/id.ts`, whose argument is type-constrained to your declared table names and Convex system table names.

```ts confect/tables/notes.ts
import { Table } from "@confect/core";
import * as Schema from "effect/Schema";
import { Id } from "../_generated/id";

export default Table.make(() =>
  Schema.Struct({
    userId: Schema.optional(Id("users")),
    text: Schema.String.check(Schema.isMaxLength(100)),
    tag: Schema.optional(Schema.String),
    author: Schema.optional(
      Schema.Struct({
        role: Schema.Literals(["admin", "user"]),
        name: Schema.String,
      }),
    ),
    embedding: Schema.optional(Schema.Array(Schema.Number)),
  }),
)
  .index("by_text", ["text"])
  .index("by_role", ["author.role"])
  .searchIndex("text", {
    searchField: "text",
    filterFields: ["tag"],
  })
  .vectorIndex("embedding", {
    vectorField: "embedding",
    filterFields: ["author.name", "tag"],
    dimensions: 1536,
  });
```

```ts confect/tables/users.ts
import { Table } from "@confect/core";
import * as Schema from "effect/Schema";

export default Table.make(() =>
  Schema.Struct({
    username: Schema.String,
  }),
);
```

Each `confect/tables/*.ts` file **must default-export a `Table`**—codegen reads `module.default` and applies the filename as the table name. Consumers (specs, impls, HTTP handlers, etc.) reach a table's derived `Schema`s through the generated wrapper at `confect/_generated/tables/<name>`, e.g. `import notes from "../_generated/tables/notes"` and then `notes.Doc`.

## Deploy checks

A table can carry deploy checks: checks of its declaration alone, whose verdict no call, document or setting can change, so they need to run only when the backend deploys. A library that extends tables, such as one that declares aggregates on them, refuses a declaration it cannot support this way. Add one with `.deployCheck`, which takes the bound table and returns its refusals, each naming what it refuses, or none when the table passes:

```ts confect/tables/days.ts
import { Table } from "@confect/core";
import * as Schema from "effect/Schema";

export default Table.make(() => Schema.Struct({ day: Schema.String }))
  .index("by_day", ["day"])
  .deployCheck((table) =>
    Object.keys(table.indexes).length > 16
      ? [`${table.tableName} declares more than 16 indexes`]
      : [],
  );
```

Making, binding or chaining a table runs no check and builds no schema, and a table may carry several checks, which run in the order they were added. They run where the backend's Convex schema is built:

- **At a push.** `Table.tableDefinition` from `@confect/server` runs a table's checks before it builds its Convex definition, and every generated `_generated/convexSchema.ts` builds each table's definition through it. Convex evaluates the app's schema and each component's while it analyzes a push, before it accepts it, so a refusal fails the push and the deployment keeps serving the last push that succeeded. That holds for a component with tables and nothing else, which has no function or router to run a [push check](/server/backend-declaration#refuse-a-push). The refusal is a `TableRefused`, which names the table and each refusal:

  ```
  InvalidSchema: Hit an error while pushing:
  Uncaught TableRefused: Table "days" is refused: days declares more than 16 indexes
  ```

- **In codegen.** Once it has written the generated files, `confect codegen`, and so `confect dev`, runs the checks of every table the backend's schema binds and fails with `TableDeployRefusedError`, naming each refused table and each refusal.
- **In tests.** A generated test subject imports its Convex schema, so importing a subject whose table is refused throws `TableRefused`. Every test layer also runs the checks of each table of the app's database schema, and of each component's whose kit gives its `databaseSchema`, as it builds, so a backend handed a Convex schema built another way refuses too. See [Push checks](/guides/testing#push-checks).

No call runs them: a function binds the tables it reads but never builds the Convex schema, so a call pays nothing for a check. A table a table module builds but leaves out of the schema, such as a named export beside its default, is never deployed, and nothing runs its checks. A section that [wraps the deployment schema](/server/backend-declaration#wrap-the-deployment-schema) must call `Table.tableDefinition` on each table it is passed, so the checks still run at a push. `Table.deployRefusals(table)` runs a table's checks and returns their refusals, and `Table.verifyDeploy(table)` returns them as a `Result` failing with `TableRefused`.

## Document IDs

Import `Id` from `confect/_generated/id` for both ID schemas and TypeScript types:

```ts
import * as Schema from "effect/Schema";
import { Id } from "./confect/_generated/id";

const noteArgs = Schema.Struct({ noteId: Id("notes") });
type NoteProps = { noteId: Id<"notes"> };
```

Use `Id("notes")` when you need a schema and `Id<"notes">` when you need a type. Both accept only your declared table names and Convex's system table names, `"_storage"` and `"_scheduled_functions"`. For example, use `Id("_storage")` for a stored file reference and `Id<"_storage">` for its TypeScript type.

When you only need the type, use a type-only import. It adds no runtime dependency and works in frontend code:

```ts
import type { Id } from "./confect/_generated/id";

type NoteProps = { noteId: Id<"notes"> };
```

These types are compatible with Convex's generated `Id` types. IDs remain strings at runtime; a TypeScript annotation or cast does not validate an external string or check whether a document exists.

## Commit timestamps

Declare a field with `CommitTs` to store the commit timestamp of the mutation that writes it. The field compiles to Convex's `v.commitTs()`, and an index on it orders documents by commit order. A plain `Schema.BigInt` field still compiles to `v.int64()`.

```ts confect/tables/auditEntries.ts
import { CommitTs, Table } from "@confect/core";
import * as Schema from "effect/Schema";

export default Table.make(() =>
  Schema.Struct({
    action: Schema.String,
    committedAt: CommitTs.CommitTs,
  }),
).index("by_committedAt", ["committedAt"]);
```

The commit timestamp is unknown until the mutation commits. To write it, pass the database writer's `vars.commitTs` placeholder:

```ts
const writer = yield * DatabaseWriter;
yield *
  writer
    .table("auditEntries")
    .insert({ action, committedAt: writer.vars.commitTs });
```

Later queries and mutations read the field as a `bigint`. Inside the mutation that wrote it, the field still holds the placeholder, which throws if you use it as a number. The field's type is `bigint | CommitTsPlaceholder`, as in Convex, so narrow it with `typeof committedAt === "bigint"` before you compare or format it.

## Deriving table `Schema`s

### Fields

A `Table`'s `Fields` property contains an Effect `Schema` for the user-defined fields of a table.

### Doc

A `Table`'s `Doc` property contains an Effect `Schema` for the table's document, meaning the table's user-defined `Fields` plus its system fields (`_id` and `_creationTime`).

## Document types

`Fields` and `Doc` are runtime `Schema`s—_values_. Reach for them whenever you need a value: a spec's `returns`, an HTTP endpoint's `addSuccess`, or decoding. Their TypeScript types are available as `typeof notes.Doc.Type` and `typeof notes.Fields.Type`.

When you only need to annotate something with a table's document _type_, codegen also emits named document types in `confect/_generated/docs.ts`—one per table (`NotesDoc`, `UsersDoc`, …) plus a `Docs` registry:

```ts confect/_generated/docs.ts
import type { Document } from "@confect/server";
import type schemaDefinition from "./schema";

export type NotesDoc = Document.Document<typeof schemaDefinition, "notes">;
export type UsersDoc = Document.Document<typeof schemaDefinition, "users">;

export interface Docs {
  notes: NotesDoc;
  users: UsersDoc;
}
```

`NotesDoc` is the decoded document—the table's fields plus its system fields—exactly the same type as `typeof notes.Doc.Type`, but as a _named_ type. Because it's named, it keeps editor hovers and emitted `.d.ts` files readable (`NotesDoc` rather than the fully-expanded row), and it's what lets the `DatabaseReader`/`DatabaseWriter` services hand documents back under their table's name.

```ts
import type { NotesDoc } from "./confect/_generated/docs";

const renderNote = (note: NotesDoc) => note.text;
```

You can also write the type inline with the same helper the generated types alias, `Document.Document<typeof schemaDefinition, "notes">`, and drop the system fields with `Document.WithoutSystemFields<NotesDoc>`.

As a rule of thumb: reach for `notes.Doc` when you need a **value** (a `Schema`), and `NotesDoc` when you need a **type**.

<Note>
  Each type's name is the table name folded to PascalCase, so `user_profiles`
  and `userProfiles` would both produce `UserProfilesDoc`. Codegen reports an
  error if two tables would collide on the same name.
</Note>
