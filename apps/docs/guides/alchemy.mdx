`@confect/alchemy` integrates Convex cloud deployments with [Alchemy](https://alchemy.run). Use `Convex` resources for plain Convex applications, or `Confect.Backend` to run Confect codegen before pushing your backend. Your existing tables, specs, impls, and client code do not change.

This integration supports Alchemy `2.0.0-beta.86` and Effect v4. It does not infer infrastructure from your function implementations. With `alchemy dev`, the same resources run against a local Convex backend instead of Convex cloud; see [Develop locally](#develop-locally).

## Install

Install the integration and Alchemy in the workspace that contains your stack:

```sh
pnpm add -D @confect/alchemy alchemy@2.0.0-beta.86
```

The backend workspace must also have `convex` and, for `Confect.Backend`, `@confect/cli` installed. Deployment uses these installed binaries; it does not download a CLI. Use Node.js 24 or later.

## Deploy to an existing backend

Set `CONVEX_DEPLOY_KEY` in your shell or CI secret store to a deployment-specific key. Do not use a project-level preview key: the deployment must already exist.

Create `alchemy.run.ts`:

```ts
import { Confect, Convex } from "@confect/alchemy";
import * as Alchemy from "alchemy";
import * as Config from "effect/Config";
import * as Effect from "effect/Effect";

export default Alchemy.Stack(
  "Notes",
  {
    providers: Convex.providers(),
    state: Alchemy.localState(),
  },
  Effect.gen(function* () {
    const backend = yield* Confect.Backend("Backend", {
      deployment: {
        name: "happy-animal-123",
        url: "https://happy-animal-123.convex.cloud",
      },
      deployKey: yield* Config.Redacted("CONVEX_DEPLOY_KEY"),
      cwd: "apps/backend",
    });

    return { url: backend.url };
  }),
);
```

Replace the name, URL, and working directory with your deployment's values. Regional Convex cloud URLs are supported. This stack does not take ownership of the existing project or deployment, and it does not require a management token.

Run the stack from the directory containing `alchemy.run.ts`:

```sh
pnpm alchemy deploy
```

`Confect.Backend` runs `confect codegen`, then `convex deploy`. A codegen failure prevents the push. The deploy key selects the target explicitly, independently of the backend directory's environment files.

<Warning>
  Treat Alchemy state as a secret store. Deploy keys and managed environment
  values are persisted in state; `Redacted` hides ordinary rendering, not
  storage. Protect the state backend and its backups, and never commit
  `.alchemy/` or return credentials as stack outputs. The example uses local
  state; choose an appropriately secured shared state backend for CI.
</Warning>

## Provision a project and deployment

To manage infrastructure too, set `CONVEX_ACCESS_TOKEN` to a team access token and `CONVEX_TEAM_ID` to your team ID. Convex recommends a service account for long-lived automation; see [Platform APIs](https://docs.convex.dev/platform-apis).

Replace the stack body with:

```ts
Effect.gen(function* () {
  const project = yield* Convex.Project("Project", {
    teamId: yield* Config.Number("CONVEX_TEAM_ID"),
    name: "notes-production",
  });

  const deployment = yield* Convex.Deployment("Deployment", {
    projectId: project.projectId,
    type: "prod",
    reference: "notes-production",
  });

  const key = yield* Convex.DeployKey("DeployKey", {
    deploymentName: deployment.name,
    allowedActions: [
      "deployment:deploy",
      "deployment:env:view",
      "deployment:env:write",
    ],
  });

  const backend = yield* Confect.Backend("Backend", {
    deployment,
    deployKey: key.deployKey,
    cwd: "apps/backend",
    env: {
      PUBLIC_ORIGIN: "https://example.com",
      SERVICE_TOKEN: yield* Config.Redacted("SERVICE_TOKEN"),
    },
  });

  return { url: backend.url };
});
```

`Backend.env` is a flat record of variable names to deployment inputs. Pass the generated `manifest` as a separate prop to type its keys and values from `confect/env.ts`. It does not accept an `Env.make` declaration or a `{ manifest, values }` wrapper. Without `manifest`, values can be strings, `Redacted<string>` values, or Alchemy inputs of either.

`env` is applied before code is pushed. Pass `backend.url` to your frontend resource's build environment, such as `VITE_CONVEX_URL`. This establishes an Alchemy dependency on backend deployment completion. Never pass the deploy key to the frontend.

One stack should own each project and deployment. For a project shared by several stages, pass its project ID to each stage's deployment rather than declaring the same project in every stage. Deployment references must be unique within the project.

For a [declared backend](/server/backend-declaration), pass its generated manifest to type the env input directly from `confect/env.ts`:

```ts
import { Confect } from "@confect/alchemy";
import * as Config from "effect/Config";
import * as Effect from "effect/Effect";
import manifest from "../backend/confect/_generated/manifest";

Effect.gen(function* () {
  return yield* Confect.Backend("Backend", {
    deployment,
    deployKey,
    manifest,
    env: {
      EMAIL_FROM: "noreply@example.edu",
      RESEND_API_KEY: yield* Config.Redacted("RESEND_API_KEY"),
      EMAIL_TRANSPORT: "resend",
    },
  });
});
```

Required keys must be present. Unknown keys, plain strings for secret fields, and values outside a field's declared literals fail to typecheck. Each value also accepts an Alchemy `Input`. Optional fields can be omitted; `env` itself can be omitted when all fields are optional. Without `manifest`, the existing untyped env record remains available. Infra imports only the generated manifest, never backend implementation code.

## Use plain Convex

`Convex.Code` runs the Convex deploy command without Confect codegen:

```ts
Effect.gen(function* () {
  const code = yield* Convex.Code("Backend", {
    deployment,
    deployKey: key.deployKey,
    cwd: "apps/backend",
  });
  return code;
});
```

You can also declare `Convex.EnvironmentVariables` separately. A standalone code resource must depend on its outputs if those variables need to be applied first; declaring resources in source order alone does not establish a dependency. `Confect.Backend` handles this ordering for its `env` option.

## Send backend logs

Declare one `Convex.LogStream` for each backend that sends logs to Axiom. Set the deployment URL and keys in your shell or CI secret store:

```ts
import { Convex } from "@confect/alchemy";
import * as Alchemy from "alchemy";
import * as Config from "effect/Config";
import * as Effect from "effect/Effect";

export default Alchemy.Stack(
  "Observe",
  { providers: Convex.providers(), state: Alchemy.localState() },
  Effect.gen(function* () {
    yield* Convex.LogStream("BackendLogs", {
      kind: "axiom",
      deploymentUrl: yield* Config.String("CONVEX_DEPLOYMENT_URL"),
      deployKey: yield* Config.Redacted("CONVEX_DEPLOY_KEY"),
      apiKey: yield* Config.Redacted("AXIOM_API_KEY"),
      datasetName: "backend",
      attributes: [{ key: "app", value: "notes" }],
    });
    return {};
  }),
);
```

If you set Axiom's `ingestUrl`, use one of its public ingest base URLs:

- `https://api.axiom.co`.
- `https://us-east-1.aws.edge.axiom.co`.
- `https://eu-central-1.aws.edge.axiom.co`.

The upstream backend source lists these three URLs. Other URLs are unverified. A wrong URL returns a plain HTTP error from Convex.

For a deployment declared in the same stack, pass `deployment.url` and `key.deployKey` instead. The deploy key must authorize log stream operations. A supplied deployment key does not require a management token. Keep the Alchemy state and its backups protected, as with deploy keys.

Use `kind: "sentry"` with a `Redacted` `dsn` and optional `tags` to opt an app into Sentry. Use `kind: "webhook"` with `url`, `format` (`"json"` or `"jsonl"`), and optional `topics` for a webhook. A URL that embeds a credential must be passed as `Redacted`, for example `Redacted.make("https://user:password@logs.example.com/token")`. Its `hmacSecret` output is `Redacted` and refreshes from Convex on provider reads and reconciliation. Keep it in protected configuration for the webhook receiver. Omit `topics` to subscribe to all topics.

All seven kinds are typed. `axiom`, `sentry`, and `webhook` are switched on. `datadog`, `postHogLogs`, `postHogErrorTracking`, and `s3Export` fail with `LogStreamNotEnabled`, which names the kind. Every API key, DSN, S3 credential, and deploy key requires `Redacted`; plain strings fail to typecheck.

Change a field or connector secret to update the stream in place. Removing an optional field clears it. A changed `kind` or `deploymentUrl` replaces the stream. Removing the resource deletes its owned stream even after an external edit. A stream already absent during removal is fine. A stream still listed as `deleting` does not block creation of another stream of that kind.

If the replacement destination already has a stream of that kind, the plan stops before it changes either stream. Resolve the destination's ownership manually before continuing.

Keep one resource per kind on a deployment. A readable field edited outside the stack stops the plan with `LogStreamDrift`. Restore that field manually before continuing. Status changes and webhook HMAC rotations do not count as drift. Write-only credentials cannot be checked for external changes because Convex does not return them.

A deleted stream or an existing stream without an ownership record stops the plan with `LogStreamRecoveryRequired`. Restore the protected state or resolve the remote stream manually before continuing. The resource never adopts an existing stream, even with Alchemy adoption enabled, and never silently recreates a deleted one.

The lifecycle is tested against a fake Convex API through Alchemy plan and apply. The following remain unproven on a real account:

- Delivery to Axiom or Sentry, and delivery to a webhook receiver.
- The event envelope and webhook signature verification.
- Delivery retries and backoff.
- Cloud plan entitlements and permissions for log streams.

## Develop locally

Run the same stack with `alchemy dev` to develop against a local Convex backend:

```sh
pnpm alchemy dev
```

Under `alchemy dev`, `Convex.providers()` resolves each `Convex` resource to a local implementation. Your stack definition does not change. Project and deployment provisioning need no account credentials:

- `Convex.Deployment` downloads the Convex backend release `precompiled-2026-10-28-cccbade` into the Convex CLI's binary cache and runs it on `127.0.0.1`. The deployment's `url` points at the local backend.
- `Convex.DeployKey` returns the local backend's admin key. It grants full access to that backend whatever `allowedActions` you request.
- `Convex.Project` returns a local placeholder and does not contact Convex.
- `Convex.EnvironmentVariables`, `Convex.Code`, and `Confect.Backend` set variables and push code to the local backend, in the same order as in the cloud.
- `Convex.LogStream` uses the local deployment URL and admin key. Connector credentials still come from your stack configuration. Local mode does not substitute a local Axiom or Sentry service.

An existing local deployment keeps its old backend and must be recreated to get Convex 1.49 support.

Values your stack reads with `Config`, such as `CONVEX_TEAM_ID`, must still resolve in development. Give them a development default or set them in your shell.

The backend keeps running while `alchemy dev` reloads your stack and stops when you end the session. If it exits or fails to start, the next reload starts it again. Its data, environment variables, and credentials are kept in `.alchemy/convex/<stack>/<stage>/<deployment>` and reused the next time you run `alchemy dev`, on the same ports and URL. Only one session can serve a data directory at a time.

Removing the deployment from your stack keeps its data; `RemovalPolicy.destroy()` deletes it. If you lose your Alchemy state, the next `alchemy dev` creates a new deployment, and the old data directory stays until you delete it. Removing `Convex.EnvironmentVariables` while its backend is not running drops them from your Alchemy state but leaves them set in the kept data.

Alchemy does not run `confect dev` or `convex dev` for you. `Confect.Backend` runs one-shot `confect codegen` before each push. Run `confect dev` separately if you need continuous generated-file updates; it does not trigger Alchemy to push.

Code is pushed each time the stack applies. `alchemy dev` re-applies when a file your stack imports changes; after editing Convex functions that your stack does not import, save `alchemy.run.ts` or restart `alchemy dev` to push them.

Pushes to one deployment wait for each other, locally and in the cloud, so two resources, stacks, or checkouts never push to the same deployment at the same time. The locks live in your user cache directory (`~/.cache/confect/alchemy/locks`, or `%LOCALAPPDATA%\confect\alchemy\locks` on Windows), so they coordinate every process that shares it. Pushes from a different user, a different home directory, or a different machine, such as two CI jobs, are not coordinated. If the `alchemy` process is killed outright, for example with `kill -9`, a push it started can finish without holding the lock; let it finish before pushing again.

By default the backend binds two free ports chosen by the operating system. A deployment keeps its ports once the backend has started on them, so a failed first start picks new ones. If another program has taken one of the kept ports, `alchemy dev` fails rather than moving the backend; free the port and run it again. To pick ports from a range instead, set `CONFECT_LOCAL_BACKEND_PORTS`:

```sh
CONFECT_LOCAL_BACKEND_PORTS=3300-3399 pnpm alchemy dev
```

Each data directory keeps running the backend release that created it, even after a later version of this integration pins a newer release. To move a deployment to the newer release, delete its data directory.

<Warning>
  The data directory contains the local backend's admin key and instance secret.
  Keep `.alchemy/` out of version control. Local backends listen on `127.0.0.1`
  only, but the backend receives its instance secret as a command-line argument,
  which other users of the same machine can see in the process list.
</Warning>

## Run each mount's `init`

Each push runs the `init` of every [mount](/server/components) whose component declares one. It runs after the code push and before the push releases the deployment's lock, so no other push lands between this push's code and its `init`. Mounts run one at a time, in the order `App.make` lists them. A Confect component that mounts components of its own runs their `init` after its own, at their nested component path, such as `relay/inbox`.

`confect codegen` writes the steps into `convex/confectDeploy.ts`, an internal mutation that makes each mount's callback handles, and imports each mount from `confect/<name>.ts`. Run codegen for each component directory before its parent's, so the parent finds the component's own `confectDeploy.ts`.

Each `init` is its own transaction. When one fails, the push fails with `bulkEmail: init failed; earlier mounts are applied, and the next push retries`. Mounts before it keep their new config, and it and the mounts after it keep their old config. The next push runs every `init` again and converges, so write `init` to be safe to run twice. A callback target that is no longer deployed fails the push at its mount, before that mount's `init` runs.

New code can serve requests briefly before its mounts' `init` has run. Write handlers that tolerate the previous config.

A push outside Alchemy, such as `convex deploy` or `convex dev`, does not run `init`, and is unsupported for a backend whose mounts declare one. `confect dev` does not push, so it runs no `init` either.

## Understand updates and deletion

Code is pushed on every Alchemy deployment, including when resource props have not changed. This deliberately catches source-only edits, workspace dependency changes, and out-of-band code pushes without relying on an incomplete file hash. Convex still performs its normal validation and deployment checks. Removing `Code` or `Backend` does not erase deployed functions or data.

Projects and deployments **retain their cloud objects by default** when removed or destroyed. Alchemy drops the state entry, so managing a retained object again requires explicit adoption. To authorize deletion, use Alchemy's `RemovalPolicy.destroy()` on the resource. Deleting a project also deletes its deployments and data, even if an individual deployment was retained. Back up data before opting into deletion.

The provider refuses project-team changes and deployment identity changes that could move or replace data. Create a separate resource and plan a migration instead. Existing resources found by name or reference require explicit Alchemy adoption; ambiguous matches fail rather than selecting an arbitrary object.

Environment management preserves unrelated variables. Existing variables that overlap a new declaration require explicit adoption. Adopted values are restored when their ownership is removed; variables introduced by the stack are removed. Pass secrets as `Redacted` values, not plain strings.

Set `env: {}` to remove all managed variables before the next code push. Removing the `env` option removes the environment resource instead, so its cleanup follows Alchemy's resource-deletion ordering.

Deploy-key secrets are only available when created. If the key's saved secret is lost, or the managed key no longer exists, deployment fails rather than silently rotating credentials. Restore the protected state or explicitly provision a replacement key. Deploy keys are revoked when their resource is destroyed.

After upgrading to the fork based on upstream 10.3.1, regenerate with `confect codegen` before using the backend's generated files. `Confect.Backend` also regenerates them on its next apply.

## Troubleshoot a failed push

Command failures identify the phase and exit status. A failed `init` names its mount, and its `detail` carries the error Convex reported. Child-process output is suppressed to avoid exposing credentials through CLI diagnostics. Run `confect codegen` or the Convex deploy command directly in a trusted terminal to inspect the underlying error. Keep deploy keys out of command arguments and terminal recordings.

The integration does not bypass Convex's schema checks or large-index safeguards. Code and environment updates are separate operations, not a transaction: an environment update may have succeeded even if the subsequent code push fails.
