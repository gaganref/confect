`@confect/test` wraps [`convex-test`](https://docs.convex.dev/testing) with Effect-native APIs. It provides a `TestConfect` service that lets you call your Confect functions using refs, run arbitrary mutation-context code for test setup, and test with user identities.

## Installation

<CodeGroup>

```bash pnpm
pnpm add -D @confect/test convex-test @effect/vitest
```

```bash npm
npm install -D @confect/test convex-test @effect/vitest
```

```bash yarn
yarn add -D @confect/test convex-test @effect/vitest
```

```bash bun
bun add -D @confect/test convex-test @effect/vitest
```

</CodeGroup>

## Setup

Create a `TestConfect.ts` file that configures the test layer with your generated runtime schema, generated Convex schema definition, and Convex modules. Both schemas are emitted by `confect codegen` from `confect/tables/*.ts`; you never edit them by hand.

```ts test/TestConfect.ts
/// <reference types="vite/client" />

import { TestConfect as TestConfect_ } from "@confect/test";

import confectSchema from "./confect/_generated/schema";
import convexSchema from "./confect/_generated/convexSchema";

export const TestConfect = TestConfect_.TestConfect<typeof confectSchema>();

export const layer = TestConfect_.layer(
  confectSchema,
  convexSchema,
  import.meta.glob("./convex/**/!(*.*.*)*.*s"),
);
```

For a [declared backend](/server/backend-declaration), codegen also writes a test-only registry. Pass the generated app to register the app's components and their nested installations automatically. Mount names and HTTP prefixes come from the declaration; tests need no `register` callback or `httpMounts` list.

```ts
import { TestConfect } from "@confect/test";
import app from "../confect/_generated/testing.js";

export const Test = TestConfect.TestConfect<typeof app.schema>();
export const layer = TestConfect.layer(app);
```

The generated registry imports the schema and lazy module loaders of each local Convex component by a relative path. Beside each module it reads that module's source from disk, so the test kernel finds its `"use node"` directive as Convex's bundler does. For a component mounted from another package, codegen tries `<package>/testing`, then `<package>/test`. It prefers `/testing` when both resolve. The registry imports the selected namespace as a mount-named kit, such as `workpoolKit`, and calls its `register(t, name)`. That kit also registers the package's nested components. `TestConfect.layer` names the mount if the kit exports neither `register` nor both `schema` and `modules`.

When a package's own kit is missing or wrong, the component's descriptor names the kit to use instead, by package specifier:

```ts
export default Component.make("aggregate", {
  client: Client.make,
  testing: "@acme/aggregate/testing",
});
```

Codegen then imports that kit for every mount of the descriptor from another package, at any depth, a nested component's own declaration included, and skips the `<package>/testing` and `<package>/test` search. A local component's mount ignores it. It fails, naming the mount and the kit, when the specifier is a relative or absolute path, does not resolve from `convex/convex.config.ts`, or lists its exports without a `register`.

Local kits use names such as `emailSchema` and `emailKit`. Repeated mounts of one definition share the first mount's kit, which each mount calls with its own path, so each mount loads its own copy of the component's modules, as the next section sets out. Codegen sanitizes identifiers, adds suffixes on collision, and writes imports before local kit declarations. Relative imports carry `.js` extensions for NodeNext. Module-map keys retain their source extensions, such as `mail.ts`. When neither public test entry resolves, codegen reports both entries it tried. It never writes another package's private file paths.

Keep the registry in test imports only. It is separate from the runtime schema and function wrappers, so production functions retain their per-group bundles. Regenerate it when adding functions or changing component installations. The schema-based constructor above remains available for hand-written component kits and custom HTTP router loaders.

You can also pass an authored `App` value with its registry as `TestConfect.layer(app, registry)`. This reads mount names and HTTP prefixes from that value. Prefer the generated one-argument form when a component definition has nested `use` calls; codegen evaluates those definitions with Convex's config loader. The test layer retains the shared process-env and module-cache limitations described below.

Every time the `TestConfect` layer is constructed, a new test database is created. If you want a clean database for each test, provide the layer on a per-test basis (as shown below). If you want to share state across tests in a describe block, you can provide the layer at a higher scope instead.

## Writing tests

Use `@effect/vitest`'s `it.effect` to write effectful tests. Yield `TestConfect` from the service, then call your functions using refs.

```ts test/notes.test.ts
import { describe, it } from "@effect/vitest";
import { assertEquals } from "@effect/vitest/utils";
import * as Effect from "effect/Effect";

import refs from "./confect/_generated/refs";
import * as TestConfect from "./TestConfect";

describe("notes", () => {
  it.effect("can insert and list notes", () =>
    Effect.gen(function* () {
      const c = yield* TestConfect.TestConfect;

      yield* c.mutation(refs.public.notes.insert, {
        text: "Hello",
      });

      const notes = yield* c.query(refs.public.notes.list, {});

      assertEquals(notes.length, 1);
      assertEquals(notes[0]?.text, "Hello");
    }).pipe(Effect.provide(TestConfect.layer)),
  );
});
```

## Deployment signing keys

`TestConfect.jwks()` wraps [`convex-test`](https://docs.convex.dev/testing/convex-test)'s `t.jwks()` in a lazy `Effect<DeploymentJwks>` instead of a Promise. Native rejections become defects. The `DeploymentJwk` and `DeploymentJwks` types are re-exported from `@confect/test/TestConfect`.

```ts
Effect.gen(function* () {
  const c = yield* TestConfect.TestConfect;
  const jwks = yield* c.jwks();
  return jwks;
});
```

## Calling functions

`TestConfect` provides `query`, `mutation`, and `action` methods that accept a ref and args, returning an `Effect` with the decoded result.

```ts
Effect.gen(function* () {
  const c = yield* TestConfect.TestConfect;

  const notes = yield* c.query(refs.public.notes.list, {});

  const noteId = yield* c.mutation(refs.public.notes.insert, {
    text: "Hello",
  });

  const result = yield* c.action(refs.public.random.getNumber, {});
});
```

## Typed errors

When a ref's spec declares an `error` schema, the decoded error is added to the error channel of `query`, `mutation`, and `action` alongside `ParseError`. See [Error Handling](/server/error-handling) for how to declare error schemas.

```ts
import { describe, it } from "@effect/vitest";
import { assertFailure } from "@effect/vitest/utils";
import type { GenericId } from "convex/values";
import * as Effect from "effect/Effect";

import { NoteNotFound } from "./confect/notes.spec";
import refs from "./confect/_generated/refs";
import * as TestConfect from "./TestConfect";

describe("notes", () => {
  it.effect("returns NoteNotFound for a missing id", () =>
    Effect.gen(function* () {
      const c = yield* TestConfect.TestConfect;

      const result = yield* c
        .query(refs.public.notes.getOrFail, {
          noteId: "missing" as GenericId<"notes">,
        })
        .pipe(Effect.result);

      assertFailure(result, new NoteNotFound({ noteId: "missing" }));
    }).pipe(Effect.provide(TestConfect.layer)),
  );
});
```

## Running setup code

Use `run` to execute arbitrary code with mutation-context services (like `DatabaseWriter`) for test setup. When the handler returns a value, pass a `Schema` as the second argument for decoding.

```ts
import { Id } from "./confect/_generated/id";
import { DatabaseWriter } from "./confect/_generated/services";

Effect.gen(function* () {
  const c = yield* TestConfect.TestConfect;

  const noteId = yield* c.run(
    Effect.gen(function* () {
      const writer = yield* DatabaseWriter;

      return yield* writer.table("notes").insert({ text: "seed data" });
    }),
    Id("notes"),
  );
});
```

When the handler returns `void`, the second argument can be omitted.

```ts
Effect.gen(function* () {
  const c = yield* TestConfect.TestConfect;

  yield* c.run(
    Effect.gen(function* () {
      const writer = yield* DatabaseWriter;

      yield* Effect.forEach(items, (item) =>
        writer.table("notes").insert(item),
      );
    }),
  );
});
```

## Testing with user identity

Use `withIdentity` to scope function calls to a specific user identity.

```ts
Effect.gen(function* () {
  const c = yield* TestConfect.TestConfect;

  const asUser = c.withIdentity({
    subject: "user-123",
    tokenIdentifier: "https://example.com|user-123",
    email: "user@example.com",
  });

  const identity = yield* asUser.query(refs.public.auth.getIdentity, {});
});
```

## Testing HTTP endpoints

Use `fetch` to test your [HTTP API](/server/http-api) endpoints.

```ts
Effect.gen(function* () {
  const c = yield* TestConfect.TestConfect;

  const response = yield* c.fetch("/api/get-first");
  const body = yield* Effect.promise(() => response.json());
});
```

### Register component test kits

Pass an options object with a `register` callback as the fourth argument to `TestConfect.layer`. It runs synchronously during layer construction, after the test backend exists and before the service is available. The callback receives a registration function for the component's Convex schema and module loaders. A component package's test entry takes it as `t.registerComponent`.

```ts test/TestConfect.ts
import { TestConfect } from "@confect/test";
import { register } from "@example/counter/test";
import applicationSchema from "./confect/_generated/schema";
import convexSchema from "./confect/_generated/convexSchema";

export const layer = TestConfect.layer(
  applicationSchema,
  convexSchema,
  import.meta.glob("./convex/**/!(*.*.*)*.*s"),
  {
    register: (registerComponent) => {
      register({ registerComponent }, "counter");
    },
  },
);
```

Use the same component path as the installation in `convex.config.ts`. A package's `register` installs its own nested components under that path. Register any other nested component with its full path, such as `"counter/child"`. Once registered, call bound references with `query`, `mutation`, and `action`. You can also register after setup with the existing effectful `registerComponent` method.

### Fetch mounted component routes

Add `httpMounts` to describe the routes your application exposes. TestConfect does not evaluate `convex.config.ts`. Each descriptor pairs a registered `componentPath` with its `httpPrefix`.

```ts
const layer = TestConfect.layer(
  applicationSchema,
  convexSchema,
  applicationModules,
  {
    register: (registerComponent) => {
      register({ registerComponent }, "first");
      register({ registerComponent }, "second");
    },
    httpMounts: [
      { componentPath: "first", httpPrefix: "/email" },
      { componentPath: "second", httpPrefix: "/other-email" },
    ],
  },
);

const program = Effect.gen(function* () {
  const c = yield* TestConfect.TestConfect<typeof applicationSchema>();
  return yield* c.fetch("/email/webhook", { method: "POST", body: "payload" });
}).pipe(Effect.provide(layer));
```

`fetch` selects the longest matching prefix at a path segment boundary. `/email/webhook` and the bare `/email` path match `/email`; `/emails/webhook` does not. The bare-prefix behavior can differ from Convex's trailing-slash mount routing. Trailing slashes on prefixes are ignored. Each prefix must be unique and start with `/`, without a query or fragment. Unmatched requests use the application's HTTP module as before. A mounted request does not require an application HTTP module. For a nested component, use its full host-visible prefix, such as `/parent/child`. This explicit table selects mounts before application routes; it does not reproduce Convex's full configuration and route precedence.

The selected component receives its own action context. Route lookup uses the path after the prefix, while the handler receives the full mounted request URL. During HTTP module construction and handler execution, `CONVEX_SITE_URL` is the application's site URL plus the mount prefix. Set the application's `CONVEX_SITE_URL` before fetching if you need a specific origin; otherwise TestConfect uses `https://some.convex.site`. The previous environment value is restored after the request, including when construction fails. `withIdentity` accessors use the same mounts; components still have no application auth capability.

### Construct a router for each mount

HTTP layers can read configuration while their module is constructed. ES imports cache modules across installations and tests. For two mounts of the same component, provide a module loader that constructs a fresh router. Keep the router factory in a separate module from the production HTTP entry point:

```ts src/test.ts
import type { TestConfect } from "@confect/test";
import schema from "./convex/schema";

const modules = import.meta.glob("./convex/**/!(*.*.*)*.*s");

export const register = (
  t: { readonly registerComponent: TestConfect.RegisterComponent },
  name: string,
) => {
  t.registerComponent(name, schema, {
    ...modules,
    "./convex/http.ts": () =>
      import("./confect/httpFactory").then(({ makeHttp }) => ({
        default: makeHttp(),
      })),
  });
};
```

`makeHttp` must construct `HttpRouter.make(componentSchema, routes)` and any configuration-dependent route layers on each call. The production `confect/http.ts` can export `makeHttp()` as its default. TestConfect caches each mount's resulting router, including construction failures. A plain dynamic import of an already constructed router cannot provide separate construction-time configuration for two mounts.

<Warning>
  Mounted HTTP tests share the process environment. Fetches through one layer,
  including its identity accessors, run sequentially. Other layers and
  concurrent queries, mutations, or actions can still observe the temporary
  environment. Component modules can also see application environment variables.
  Run tests that need environment isolation on a local Convex backend.
</Warning>

The mounted bridge buffers request and response bodies and reconstructs response headers. It does not test streaming or repeated response headers faithfully. `originalUrl` retains the mount path and query, but its origin comes from the test site URL, not a real incoming connection. Module imports that already captured configuration keep those values. Use local-backend tests for behavior that depends on these differences.

## Push checks

A backend's [push checks](/server/backend-declaration#refuse-a-push) refuse a push whose source they refuse. A test backend never pushes, so every test layer runs them itself when it builds: `TestConfect.layer`, on either target, and the `layer` of a generated `TestBackend` or component subject. Building runs each check registered for the app's schema and for each component a kit registers, once per build, before the layer serves any call, an HTTP request included. A component the test registers later with `registerComponent` runs its checks as it registers. These runs are apart from the memo Convex's analysis runs a check through, so a test that builds several backends over one module graph runs the checks once for each.

A refusal is a defect of the backend under test, as a refused push is of a deployment, so building dies with `PushRefused`, which names the check and each refusal. Building also dies with `NoPushEntry` when checks are registered for the app's schema, or a component's, but none of its functions or routers runs them, since no push would run them either. The error names the component. The layer finds a component's schemas from the component's own modules: each schema a module registers checks for at its top level belongs to that module, and a component owns every schema registered by any module its loaded modules import, at any depth, as Vitest's module graph shows them. So two components whose entries import one provider both own its schema, even once the provider is cached, and every kit, generated or packaged, is checked with no option. Outside Vitest, the layer sees only registrations made while it loads a module, so a kit whose modules were evaluated before and outside any layer passes the schema as `databaseSchema` in `registerComponent`'s options, or in a kit's `{ schema, modules }`. A backend with no registered check builds as before.

The layer evaluates the backend's modules to find the checks: the kernel loads them under its own rules, and its open reuses that load, while convex-test's target imports each module Convex would deploy. A mounted component's router is built during the build, and its first request reuses that router, so a router that is a component's only checked entry, or the only module that registers its checks, refuses the build too. It builds as its mount's deployment does: its code reads the mount's site URL as `CONVEX_SITE_URL`, while the host's environment, which concurrent backends read, stays as it is. On the kernel it also loads under the component's environment, the isolate's guards and the backend's seeded random stream, as the component's modules do. A module that fails to load, whether its loader rejects or throws, does not fail the build. It fails the call that loads it, as before.

To assert that a build refuses, take its exit:

```ts
const exit = yield * Effect.exit(Layer.build(layer));
assert(Exit.isFailure(exit));
expect(Cause.hasDies(exit.cause)).toBe(true);
expect(Cause.squash(exit.cause)).toEqual(
  PushCheck.PushRefused.make({
    check: "authz",
    refusals: ["declaration tasks.read refuses"],
  }),
);
```

A test that builds a refused source on purpose, such as one that asserts a call's own refusal, passes `pushChecks: "skip"`:

```ts
const layer = TestConfect.layer(schema, convexSchema, modules, {
  pushChecks: "skip",
});
```

Call `Preflight.run(modules, { schema })` only for a backend built another way, such as `convexTest` directly, before its first call.

## Testing scheduled functions

`TestConfect` provides helpers for advancing scheduled functions in tests.

```ts
Effect.gen(function* () {
  const c = yield* TestConfect.TestConfect;

  yield* c.finishInProgressScheduledFunctions();

  yield* c.finishAllScheduledFunctions(() => {
    vi.advanceTimersByTime(5000);
  });
});
```

### Declare self-rescheduling functions

Some components schedule their own next run forever, such as the crons component's `public:rescheduler`. A component's test kit declares those functions as `module:export` in `registerComponent`'s `standing` option:

```ts
t.registerComponent(name, schema, modules, {
  standing: ["public:rescheduler"],
});
```

convex-test ignores the option. Confect's in-process test kernel does not count a standing job as work `finishAllScheduledFunctions` must finish, so the drain ends with the next run pending. Without the declaration the kernel's drain stops after 100 jobs and fails with `DrainBudgetExceeded`.

### Run on the test kernel

`TestConfect.layer` runs on convex-test unless you pass `target: "kernel"`. The option is the last argument of each form:

```ts
TestConfect.layer(registry, { target: "kernel" });
TestConfect.layer(app, registry, { target: "kernel" });
TestConfect.layer(schema, convexSchema, modules, {
  target: "kernel",
  register,
});
```

On the kernel, scheduled functions run on the kernel's own clock and never on a host timer, so `finishAllScheduledFunctions` does not call its `advanceTimers` callback. The default kernel clock follows the test's `Date`, fake timers included, so advancing fake timers and then calling `finishInProgressScheduledFunctions` runs the jobs that came due. A layer on one target can be provided inside a layer on the other, and each keeps its own backend while both are live. The option goes away once the kernel replaces convex-test.

As on Convex, a query or mutation on the kernel cannot use `fetch` or host timers: `fetch` and a multipart `formData()` reject with the errors Convex gives, and `setTimeout` or `setInterval` fails the function at once, even while it awaits the timer. Move that work to an action. Queries, mutations and actions other than Node actions also find no `setImmediate`, `queueMicrotask` or `MessageChannel`, as in Convex's runtime, and neither does a module's top level while it loads, unless the module has a `"use node"` directive. List `@confect/test/setup` first in your Vitest `setupFiles`, so a module that keeps `fetch` or a timer when it is imported is checked too:

```ts
export default defineConfig({
  test: { setupFiles: ["@confect/test/setup"] },
});
```

The guards check each call, so a stub you install with `vi.stubGlobal` or by assignment still works outside a function and stays refused inside one. A function that redefines one of these globals while it runs, with `Object.defineProperty`, `delete` or a replacement on the global's prototype, steps outside the guards: a call it makes through the replacement is not blocked. If the replacement is still in place when the function settles, read as the function reads it, the function fails with `UnguardableGlobal`, a mutation keeps none of its writes, and the guard comes back as an own property. A replacement removed again before the function settles is not caught, and accessors that run code to fake the guard at settlement are hostile and out of scope. Replace globals between functions instead.

The same rules hold for a module's top level while the kernel loads it, unless the module has a `"use node"` directive: a top-level `fetch` rejects with the same `TypeError`, and a timer the module starts fails its load, so the backend refuses to open with Convex's error. Convex loads an isolate action's module in the action's environment, where a top-level `fetch` completes. The kernel loads every module before it knows what the module exports, so it refuses that `fetch` too. A `"use node"` module keeps Node's timers while it loads, but a top-level `fetch` in it fails the load with `UndeclaredFetch`, naming the module and the host, as an action's raw `fetch` does (see below). The kernel knows a module runs in Node from its source or from `componentRuntimes`, so pass sources for a Node module that does I/O at its top level.

A Node action runs with Node's globals, and every other function with Convex's isolate's. On the kernel a Confect action's runtime comes from its registration. A plain Convex action's comes from its module's `"use node"` directive, so pass the modules' sources, a `?raw` glob of the same files, and the kernel reads the directive as Convex's bundler does. The glob can live in any test file: the kernel matches each source to its module by its path below the directory that holds `_generated`. Each form takes them beside `target`:

```ts
const sources = import.meta.glob("../convex/**/*.ts", {
  query: "?raw",
  import: "default",
});
TestConfect.layer(registry, { target: "kernel", sources });
TestConfect.layer(app, registry, { target: "kernel", sources });
TestConfect.layer(schema, convexSchema, modules, { target: "kernel", sources });
```

Without sources, a module that exports a plain Convex action fails the first call with `ActionRuntimeUnknown`, naming the module. A component's plain actions need its sources too: a kit that can, registers with `registerComponent(name, schema, modules, { sources })`. A package's test kit registers without them, so declare the runtime its plain actions run in:

```ts
TestConfect.layer(app, registry, {
  target: "kernel",
  sources,
  componentRuntimes: { "workflow/workpool": "isolate" },
});
```

The generated test registry supplies these sources for every mount, packaged ones included (see [Packaged components' modules](#packaged-components-modules)), so a `TestBackend` session needs neither.

A source you pass raw, in a layer's `sources` or `registerComponent`'s, is the text of the module its loader loads. On the kernel, a raw source for a `.ts` or `.tsx` module that has no line starting with `import` or `export`, such as a placeholder `""` or a lone `"use node";`, fails the open with `ModuleRuntime` reason `placeholderSource`, naming the module, so a test that expects a failure cannot pass on a module that never loaded. Sources read from real files are different: an empty file there is one Convex leaves out. Wrap them in `Sources.fromFiles`, and the kernel leaves such a module unregistered as Convex does:

```ts
import { Sources } from "@confect/test";

registerComponent(name, schema, modules, {
  sources: Sources.fromFiles(
    import.meta.glob("./component/**/*.ts", {
      query: "?raw",
      import: "default",
    }),
  ),
});
```

A kit that passes a `?raw` glob should wrap it. The generated registry's sources are read from files already. Only `Sources.fromFiles` can mark a source as read from a file: a reader that copies the mark is held to the strict rule, and so is one marked by another loaded copy of `@confect/test`, whose mark this copy cannot read, so it refuses loudly rather than passing.

File storage on the kernel keeps the deployment's metadata: a stored file's `_storage` row carries a base64 SHA-256 `sha256`, its `size` and a `contentType` that is `null` when the file has none, and a `sha256` you declare to `store` must match. Uploading to a `generateUploadUrl` URL, or downloading from a `getUrl` URL, needs a real deployment, so the kernel's `fetch` refuses either with `RequiresBinary`.

The kernel's `fetch` routes a request as a deployment does: the router's own `lookup` picks the route by path and method, the handler gets the exact headers and body bytes you sent, so a route that checks a signature over the raw body behaves as it would deployed, and a request no route matches gets `404 No matching routes found`. A route that throws answers `500` with the deployment's JSON error body, `{ code, trace }` plus `data` for a `ConvexError`, instead of rejecting `fetch`; a mounted component's route answers the same on either target. Identity still comes from `withIdentity`.

The kernel also runs the cron jobs each component's `crons.ts` declares, which convex-test does not. It reads them when the backend opens and refuses a job Convex would refuse at deploy. Each run starts when Convex would start it, in UTC. An interval's first run is due at once, and each later one an interval after the previous run's time. An hourly, daily, weekly, monthly or cron-expression schedule runs at its next occurrence, delayed by a random number of seconds as Convex delays it: up to 59 for a pinned minute, up to 3599 across the hour when `minuteUTC` is left out. The kernel holds no random generator. On the kernel target, `TestConfect.layer` gives the backend a seeded random stream, and every delay draws from it, so two runs with the same seed get the same delays. The seed defaults to `0`. Pass `seed` beside `target` to draw a different stream:

```ts
TestConfect.layer(registry, { target: "kernel", seed: 7 });
```

A cron run counts as no work for `finishAllScheduledFunctions`, so a drain never runs one. Advancing fake timers and then calling `finishInProgressScheduledFunctions` runs every cron run that came due, in time order with scheduled jobs. Cron expressions with `L`, `W` and `#` run as Convex runs them.

#### Two loaded copies

An install can hold two copies of `@confect/test`, such as a hoisted copy and one nested under another package. Each copy guards its own sessions. The I/O guards, `globalThis.Convex`, the kernel's `Date`, the provider-port holder and the per-component `process.env` are one per process, installed by the copy that runs first. Each answers for the copy that owns the innermost function or module load running, whichever copy loaded first and whichever copy's session opened or closed first. A function of one copy's session that calls into the other copy's session, such as an action that runs the other session's query, reaches the inner session's database, time, environment, guards and held port calls, and keeps its own once the call returns. A copy that nothing reaches any more, such as one a test runner's watch mode or `vi.resetModules()` left behind when it reloaded the package, is released from those hooks with its modules, so reloads do not accumulate copies. The exception is a copy from an earlier release that installed those hooks first: their registries stay that copy's `Map`s, which hold every copy that registers in them, so reloads beside that copy still accumulate.

A copy older than this behaviour binds those hooks only to itself. If it loads first, opening a backend on the newer copy fails with `OlderCopyLoadedFirst`, which names the hooks the older copy holds, before the backend changes anything. If it loads second, nothing in the newer copy can tell, and the older copy's own isolate functions see Node's globals, so a test can pass that a deployment would refuse. Either way, install one copy. Find the copies with `pnpm why @confect/test` or `npm ls @confect/test`, then align the version ranges that pull each copy in, or pin one version with your package manager's `overrides`, and reinstall.

#### Reach the network from an action

Convex lets an action call `fetch`, but the kernel does not: a raw `fetch` in an action, a Node action included, fails the action with `BackendRefusal` `UndeclaredFetch`, which names the action and the host. So does a `fetch` at a `"use node"` module's top level while the kernel loads it: the refusal names the module, as no action runs yet, and the backend refuses to open with it. The request never leaves the test, so the test cannot depend on the network and a run replays. Reach a provider through a provider port instead. On the kernel each port call waits as a held command until the test answers it with the provider's outcome. Provider ports are internal to `@confect/test` until the kernel is promoted.

### Randomness on the kernel

On the kernel, every random source a function or a module reaches draws from a seeded stream: `Math.random`, `crypto.getRandomValues` and `crypto.randomUUID`, in Confect and plain Convex functions, in component functions, and in modules while they load. The stream is the bound invocation's, or else the layer's own, which `seed` starts, so two runs with the same seed draw the same values. `crypto.subtle` operations that need cryptographic randomness, such as `generateKey`, are refused as a deployment refuses them in queries and mutations. In actions, where only a real deployment can supply them, they are refused with `RequiresBinary`.

The kernel installs its own `Math` and `crypto` in each function's globals. If a test leaves either global as a property the kernel cannot replace, for example by freezing it with `Object.defineProperty`, the backend refuses with `UnguardableGlobal` before any of your code runs, rather than letting it draw from the host. Replace globals with `vi.stubGlobal` or by assignment instead. A reference to `Math.random` or `crypto` that your code takes before the kernel runs anything, such as at the top of a test file, stays the host's. Likewise, a `Math` or `crypto` that a test or setup file installs before `@confect/test` is first imported is what the kernel takes as the host's, and the kernel installs its own over it as usual. After installing both, and the guards on `fetch`, the timers and the other host APIs, the kernel runs one final read-back of every guarded global before your code runs, so a step that undid one refuses too. Test code that installs accessors which run arbitrary code to rewrite other globals during the kernel's install is hostile and out of scope beyond that one final read-back of every guarded global.

### Keep secrets out of kernel artifacts

On the kernel, a value under a `Schema.Redacted` node, which a `Schema.RedactedFromValue` field decodes to, reaches the kernel's failure reports and diffs only as `[redacted]`. The raw value stays in memory as the backend's own state, so handlers and subscriptions still read it. The layer reads the secret nodes of the app's tables from its database schema. Pass `secrets` for function arguments and return values and for component tables:

```typescript
TestConfect.layer(databaseSchema, convexSchemaDefinition, modules, {
  target: "kernel",
  secrets: {
    functions: {
      "": {
        "accounts:open": {
          args: () =>
            Schema.Struct({ token: Schema.RedactedFromValue(Schema.String) }),
        },
      },
    },
  },
});
```

`secrets` is keyed by component path (`""` for the app), then by `module:export` or table name, and each schema is a thunk the kernel builds only when it first needs it. Codegen fills the same record from your Confect specs as `secrets` in `confect/_generated/testing`, which replaces a hand-written policy. It lists each function codec that holds a secret, and each table of a local mount that does. A package mount's kit registers only Convex schemas, so its tables and functions carry no policy.

## The generated test backend

For an app that can import `@confect/test`, `confect codegen` writes `TestBackend` into `confect/_generated/testing.ts`, beside the registry. Without it the file holds the registry alone, so a backend that does not test with Confect still compiles. It follows the same `confect/app.ts` mounts and specs as the production entrypoints, and it holds:

- `groups`: every group with a public function, keyed by its path, such as `tasks/tasks`. Each has its `owner`, `"product"` or the door that hosts it, its public functions' refs, and `open`, the functions a role held for `public`, `signedIn` or `self` admits.
- `obligations`: an `access` proof per public group, `realm` when `confect/auth.ts` declares verifiers, and whatever a manifest section declares.
- `laws`: `decodes` and `idScope` for every table, and any law a section declares.
- `ports`, `manifestDigest`, `manifest` and `settings`. `manifest` is the `confect/_generated/manifest.ts` the same run wrote, which types and checks `layer`'s `mounts` and `automatic`.
- `mounts`: every installed component, in the order a push runs their `init`, with what each mount binds its component's settings to, as the backend's generated `convex.config.ts` binds them, and which of them the component requires. A binding is a literal, `{ value }`, or a setting of the backend that mounts it, `{ from }`. In format 1 an app's own mount binds no settings, so each of its open slots is bound to the deployment variable the manifest names for it, such as `{ from: "LEDGER_OBSERVE" }`, and each automatic slot to the root's own. A component binds its own mounts' slots in its `confect/app.ts`, and a slot it leaves open is bound to its promoted name in the component's env, such as `{ from: "CHILD_OPEN_SECRET" }`. A slot nothing binds, such as a provider's setting a constant choice does not name, is `{ open: true }`, and a session leaves it unset.

`TestBackend.layer` passes the registry's `secrets` to the kernel, as `TestConfect.layer` does.

A manifest section adds what Confect cannot know through `testing`, which returns owners, open functions, obligations, laws and ports. Codegen refuses a fact that names no such group, public function, table, field, index or mount, before it writes `testing.ts`. In an app an `aggregate` law names the mount that keeps the aggregate.

```ts
import { TestBackend } from "../confect/_generated/testing";

it.effect("assigns a task", () =>
  Effect.gen(function* () {
    const services = yield* Layer.build(TestBackend.layer({ config, seed }));
    yield* Effect.gen(function* () {
      const t = yield* TestConfect.TestConfect<typeof TestBackend.app.schema>();
      // ...
    }).pipe(Effect.provideContext(services));
  }),
);
```

`TestBackend.layer` opens a fresh session on the test kernel. Every module of every mount loads. Then the [push checks](#push-checks) registered for the app and each component run, and a refusal stops the session before any `init`. Then each mount's `init` runs through the deploy modules a push runs, in the order Alchemy's push runs them: a parent's `init` before the components it mounts. So a parent's `init` sees its children before theirs ran, as on a deployment. A failing `init` stops the session with `MountInitFailed`. Then `seed` runs in one mutation. `TestBackend.Session` reports each kit's standing sources, the declared cron jobs and the inits that ran.

### Configuration

A session takes every app setting from `config`, and a required one is required by type. Codegen never reads `.env` or deployment state. A missing setting fails `TestConfigMissing` with the setting, the backend that declares it and this section's link. The session sets the values for its lifetime and restores the previous ones when it closes.

The slots the manifest leaves to the deployment come from `mounts` and `automatic`, named and typed as [`Backend`](/guides/alchemy#supply-a-mounts-open-settings) takes them: `Manifest.Mounts<typeof manifest>` and `Manifest.Automatic<typeof manifest>`. `mounts` holds each mount's open slots by mount name, a nested child's under its promoted name, such as `mounts.relay.CHILD_OPEN_SECRET`. `automatic` holds the automatic slots the root declares, an app's own `Env.automatic` slots included, which `config` then does not take. Each input is required when it holds a required slot, so a component gaining a required slot breaks the test and the deployment alike. As `Backend` does, the layer refuses at compile time a mount the manifest does not list, a slot a mount does not leave open, a slot the root does not declare automatic, and the app's own automatic setting in `config`, whether the options are written inline or passed through a variable. A subject whose manifest leaves nothing open takes neither.

```ts
TestBackend.layer({
  config,
  mounts: {
    ledger: { OBSERVE: "warn" },
    relay: { CHILD_OPEN_SECRET: Redacted.make("test-secret") },
  },
  automatic: { STAGE: "test" },
});
```

The values are checked by the code `Backend` checks them with, in the same order. `undefined`, `null`, `""` and an empty `Redacted` count as missing. A missing optional slot is not written. A missing required slot, a named provider's missing required setting included, fails `TestConfigMissing`, whose `owner` names the mount and whose `supply` is where the value goes, such as `mounts.ledger.OBSERVE`. Every other refusal fails `TestConfigInvalid`, with `Backend`'s reason: `UnknownMount`, `NotOpen`, `NotAutomatic`, `PlainSecret` for a secret given a plain string, `InvalidChoice` for a provider choice the component would refuse, or `InvalidValue` for anything else of the wrong kind, such as a literals slot given a value it does not list. Both name the slot and never the value. A secret stays `Redacted` until the session writes it, and a provider choice is encoded as `Backend` writes it: a provider's name, or the JSON of `{ active, standby }` or `{ pool }`.

Each mount gets the settings it binds, as on Convex: a literal, or a setting of the backend that mounts it, the app's from `config` and the deployment variables `mounts` and `automatic` supply, and a parent component's from what its own mount bound. So each value reaches its component under the name the component reads, through every parent: `mounts.ledger.OBSERVE` as the ledger's `OBSERVE`, `mounts.relay.CHILD_OPEN_SECRET` as the relay's `CHILD_OPEN_SECRET` and its child's `OPEN_SECRET`, and `automatic.STAGE` as each one's `STAGE`. The deployment variables themselves are the stack's, so neither the app nor a component reads them. A component's module code and functions read only their own settings, beside `CONVEX_CLOUD_URL` and `CONVEX_SITE_URL`, and the app never reads a component's. That holds however calls nest: a backend opened inside another backend's function loads its modules with its own settings and under its own I/O guards, and a function called while a module loads reads its own component's settings. A module that makes a syscall while it loads, for example through a mutation context it was handed, fails as on Convex, which runs none at load. So does a call it makes through an action's `ctx.runQuery`, `ctx.runMutation` or `ctx.runAction` that an action kept, and so does a promise or timer callback the load started, however long after the load it runs. There `process.env` is a plain object of those settings, so a spread, `Object.keys` and `in` see exactly them. A required component setting left without a value fails `TestConfigMissing` naming the mount.

The kernel keeps the text of each value of a `secret` slot, from `mounts` or `automatic`, as it keeps a value under a secret node of a schema, so a failure report or artifact that holds it shows a marker in its place. Codegen binds only the mounts it reads a declaration for: the app's, and a local component's own. A packaged component's nested mounts are its kit's to register, so a packaged parent's promoted slot reaches the parent under its promoted name, and the kit decides what its children see.

### Each mount loads its own modules

A deployment evaluates each mount's modules apart, so a module-level read in a component mounted twice sees each mount's own settings. The generated registry loads each mount's copy of a local component's modules. Under Vitest, the plugin from `@confect/test/Vite` gives each mount its own copy of every file those modules import, wherever it sits: inside the component, elsewhere in the repo or in the app's own folder, as a deployment bundles them into each mount:

```ts
import { plugin } from "@confect/test/Vite";
import { defineConfig } from "vitest/config";

export default defineConfig({ plugins: [plugin()] });
```

Packages under `node_modules` stay one copy for the whole test, because the kernel itself runs on Effect, `convex` and `@confect/test`. That is a limit: a deployment evaluates each mount's packages apart, so a package's module-level state is per mount there and shared across mounts in a test. A packaged component's kit is a package too. A workspace that aliases its packages to their source passes those source directories as `plugin({ packages })`, so they stay one copy as well. Each entry must be a directory: a missing one stops the plugin, naming it. Only scripts and JSON get a copy per mount, so each mount mutates its own JSON object. An asset, WASM and a `?raw` or `?url` import stay one copy, since each exports a string, a URL or a loader. Without the plugin, the second mount of one component fails to load, naming both mounts and the module.

### Packaged components' modules

The kernel reads each module's `"use node"` directive to run a plain Convex action in Node or in Convex's isolate, so it needs every component's sources. A local component's come from its own files. A package's test kit registers its modules without them, so the registry's `packagedSources` reads each packaged mount's files, and those of every component its definition mounts, such as `pool/batchWorker` below `@convex-dev/workpool`. When a kit registers a component without sources, the session adds them at that path.

#### The supported layout

The registry reads a packaged component's files only when its layout is the one the official components use:

- The mount's `convex.config` import names a package, and the package's `exports` map resolves it, under the conditions Convex's deploy bundler uses, to one file named `convex.config.js` or `convex.config.ts`.
- No `convex.config` of the other extension sits beside that file: no `convex.config.ts` beside a `convex.config.js`, and no `.js` beside a `.ts`.
- The definition's imports, followed through the files they reach, are only `convex/server`, `convex/values` or another `convex/*` entry point, another package's `convex.config` (checked under these same rules), type-only imports, and relative imports (`./x`, `../x`) of plain files inside the same package. A plain file is named by the specifier exactly, or by the specifier plus one of the extensions esbuild tries when Convex sets none, `.tsx`, `.ts`, `.jsx`, `.js`, `.css` or `.json` (inside `node_modules`, esbuild tries `.jsx` and `.js` before `.tsx` and `.ts`), and exactly one of those paths holds anything, as `lstat` reads it, a regular file, reached through no symbolic link, in a package whose `package.json`, and any manifest between the file and the package root, has no `browser` field. A relative path goes through no `exports` map, so no export condition changes what it reaches. Codegen reads that graph with `@babel/parser`, never by running it, and fails closed: a syntax form it does not know as an edge or as type-only makes the mount unsupported. Any other import may give Convex another tree than Node does, so codegen does not read the mount: a helper package whose `convex` branch differs from its `default` one, a dynamic `import()`, a `require()`, any runtime TypeScript `import x = ...`, a `require()` one or an alias such as `import loader = require` (`import type x = ...` is erased), a free `require`, `module` or `exports` in any position that no module-level runtime binding makes local (a `declare` declaration, a type-only import, an interface, a type alias or a namespace binds nothing, as TypeScript erases it), `import.meta`, a relative import that leaves the package, names a directory, has two candidates such as `logging.js` and `logging.ts`, or enters a package with a `browser` field.
- The definition's directory holds a regular file or nothing at `http.ts`, and the same at `http.js`, as `lstat` reads them. Which of them holds a module decides whether the component serves HTTP.
- The same holds for every packaged mount below it, at any depth.

The official components follow it. `@convex-dev/workpool` 0.4.14's definition imports `convex/server` and `@convex-dev/batch-worker/convex.config.js`, and batch worker 0.2.2's imports `convex/server`, `convex/values` and `./logging.js`, which imports only `convex/values`.

Codegen resolves each `convex.config` import as Convex's deploy bundler resolves it, with the esbuild the installed `convex` pins, loaded from `convex`'s own package, on the browser platform under the `convex` and `module` conditions. So a package's `convex` branch wins over its `import` branch as it does on a deploy. A newer esbuild resolves imports a deploy does not, such as a `#/` subpath import, so a `convex` that cannot load its pinned esbuild fails `ConvexBundlerUnavailableError` at codegen. `convex dev --live-component-sources` adds a condition a deploy never uses, and the registry follows the deploy. Codegen does not mirror the rest of Convex's resolution. Code a definition builds at run time, through `eval` or `new Function`, is outside this contract on purpose: codegen reads the source, it does not run it. The modules are the files in the definition's directory that a deploy registers, by `@confect/core/DeployedModule`'s rule: codegen's walk follows no symbolic link, to a file or a directory, and a directory with a module's name is no module. A TypeScript file with no `import` or `export` line is read but never registered, so a kit whose glob loads it opens.

#### Another layout: declare its runtime

A mount in any other layout, such as a package with no `exports` map (or a null one), a definition beside a sibling of the other extension, a definition that imports a helper package, a directory or link named `http.ts` or `http.js` beside the definition, or a `#/` or relative import of a definition inside a package, is not refused at codegen. Codegen still writes `testing.ts`, reads no files for that mount or any mount below it, and records each in `packagedSources` with its package and the reason, such as `{ mount: "pool", package: "x", reason: "config-siblings" }`; a mount below it carries the package its own import names, with the reason `inside-unsupported`. `TestBackend.layer` and `TestConfect.layer` then fail in their typed channel with `PackagedLayoutUnsupported`, naming the mount, the package and the reason, until the test declares that mount's runtime:

```ts
TestBackend.layer({ config, componentRuntimes: { pool: "isolate" } });
```

With a runtime declared for every recorded mount, the session opens and runs that component's plain actions in the declared runtime. A kit's own sources come first, then `componentRuntimes`, then the registry's reads. A package the registry cannot read at all, because the deploy bundler resolves nothing for its import, Node's `node_modules` lookup finds no package, or a file cannot be read, still fails `PackagedComponentUnreadableError` at codegen, naming the mount and the package, before `testing.ts` is written: no runtime fixes it.

#### Drift detection

For each `convex.config` import the registry records the package the import names, the definition's file inside that package and the package's version, and names no installed path. On every build of `TestBackend.layer` or `TestConfect.layer`, the registry reads the package again where Node's `node_modules` lookup finds it, which no export condition changes, and the layer checks it against what codegen recorded. Every path below is relative to the package root that lookup resolves through `realpath` at open. The root's own location is not checked, so a byte-identical package moved elsewhere, with a link left at its old place, still opens, as a pnpm install's links do.

- The package is still found, at the same version.
- The bytes of every file codegen read for the mount are the same, by SHA-256 digest: the package's `package.json`, the definition, every relative file its imports reach, every `package.json` read on the way up from those to the package root, every module, and the `package.json` of the `convex` whose pinned esbuild resolved the mount.
- Every file and directory codegen walked keeps its kind and real path. That covers each file above, Convex's `package.json` included, and each directory between it and the package root: each must still be a regular file or a directory, not a symbolic link, whose real path is its own path from the resolved package root, as bytes alone do not show where a relative import from a file, or the esbuild Convex's manifest pins, resolves. Codegen refuses a file it reads through a link with `PackagedComponentUnreadableError`, Convex's `package.json` included.
- Every path codegen looked up and found nothing at, as `lstat` reads it, still holds nothing. That covers every other candidate of each relative import, such as `logging.jsx` beside an imported `logging.js`, each `package.json` the `browser` check looked for, the definition's sibling of the other extension, and whichever of its `http.ts` and `http.js` codegen found nothing at. Anything there now, a dangling link or a directory included, counts.

Any difference fails with `PackagedComponentChanged`, as when a linked package's rebuild points its export at another directory, even at the same version. That is a typed error naming the mount, the package, the file and the reason, so a test can catch it by tag:

```ts
Layer.build(TestBackend.layer({ config })).pipe(
  Effect.catchTag("PackagedComponentChanged", (changed) =>
    Effect.die(`${changed.mount}: ${changed.file} changed`),
  ),
);
```

A `convex.config` of the other extension that appears beside a recorded definition after codegen fails this way, naming the new file, as Convex would deploy it instead. So does a `logging.jsx` that appears beside a `logging.js` that `import "./logging"` resolved to, as esbuild tries `.jsx` first inside `node_modules`, and a `logging.js` replaced by a link to the same text elsewhere, whose own relative imports then resolve beside the link's target.

The check does not cover a process that changes the package's files while a layer reads them, code a definition builds at run time with `eval` or `new Function`, or esbuild's own reads beyond these, which the plain-file layout makes redundant, as it leaves esbuild nothing else to read for the definition's tree. Nor does it list a packaged component's directory again: a module added there after codegen has no source, so the kernel refuses it with `ModuleRuntime` reason `missingSource` once the kit loads it, and one the kit does not load is not registered. Rerun `confect codegen` after a package changes, as after editing a linked package's build. A registry without packaged mounts says so with `packagedSources: undefined`, and only that shape, `TestConfect.WithoutPackagedSources`, gives a `TestConfect.layer` that cannot fail this way. Any other registry type, one that records only unsupported layouts or one widened with `Omit<..., "packagedSources">` included, carries `PackagedComponentChanged | PackagedLayoutUnsupported`, `TestConfect.PackagedRefusal`, in its error channel.

Declare a supported component's runtime too when its installed modules are not the ones its kit registers, such as a kit that patches them. The runtime takes the place of the package's sources for that component path.

### Packaged components keep their secrets

A packaged Confect component's test kit hands the kernel its component's secret policy as it registers, keyed from the component: `""` for its own tables and functions, a child's name for a component it mounts. The kernel keys it at the path the kit registers.

```ts
export const secrets = {
  tables: { "": { tokens: () => Tokens.Fields } },
};
export const register = (t, name) =>
  t.registerComponent(name, schema, modules, { secrets });
```

When a mount's descriptor carries a Confect `contract`, codegen refuses a kit that exports no `secrets` with `TestKitSecretsMissingError`, and a kit whose exports it cannot list without running it, such as a CommonJS kit, with `TestKitExportsUnknownError`. Write the kit as an ES module that exports `secrets` by name, `{}` when the component holds no secret.

## The generated component subject

For a component (`App.make({ kind: "component" })`) that can import `@confect/test`, codegen writes the same `TestBackend` export, built by `TestComponent.make`. Its `kind` is `"component"`. It has no groups, and it holds:

- `functions`: every public function, keyed by `group:name`, such as `mail:send`.
- `slots`: every callback contract a handle in the component's function args or tables names, keyed by contract id. Each slot has its `contract`, the `handle` a test passes where the component takes one, and its `outcomes`: `"returned"` and each declared error tag, through nested and suspended unions.
- `init`: the component's own `init`, from its descriptor. Codegen finds the descriptor from the component's own root, the directory holding its `convex/` and `confect/`, so a nested component reads its own and never its parent's. A root whose `package.json` has a name and `exports` names it by `<package>/client`, resolved as Node resolves a package importing itself, through nested conditions and arrays. Otherwise it is `client.ts` beside `confect/`.
- `obligations`: an `export` proof per function, one `laws` proof, and a `callback` proof per slot. A component owes no access or realm proof, so its obligations cannot name either.
- `laws`, `ports`, `manifestDigest`, `manifest`, `mounts` and `settings`, as an app's subject has them. A component writes its own manifest, the one its host reads through `Component.make(name, { manifest })`, and `manifestDigest` is that manifest's digest. A component can bind its own mounts' settings in its own `confect/app.ts`, so its `mounts` carry those bindings, and each slot it leaves open is bound to its promoted name, which its host supplies on a deployment. Its layer takes those from `mounts`, typed by the component's manifest as a host's `Backend` takes them, and its automatic slots from `automatic`, as an app's does.

A slot's contract must be exported from `confect/callbacks.ts`. A handle whose contract it does not export stops codegen with `UndeclaredCallbackSlotError`. A descriptor whose `init` is no internal mutation of the component stops codegen too. Otherwise the descriptor rule is:

- A declared descriptor that doesn't resolve, or a `client.*` file that isn't a descriptor, stops codegen.
- A component that declares no descriptor at all has no `init` to lose, so it gets none. That is the layout where the host writes the descriptor inline, as `Mount.make(Component.make("counter", { client }))` in the host's `app.ts`. A manifest section may add laws and ports to a component, but no owner, open function or access obligation.

`TestBackend.layer({ config, install, seed })` opens the component as a push initialises it. It shares the app subject's session opener, so it checks each packaged mount as [Drift detection](#drift-detection) describes, takes `componentRuntimes` as an app's layer does, and can fail with `PackagedComponentChanged` or `PackagedLayoutUnsupported`. Every module loads. Then the component's own `init` runs with `install`, which is typed from `init`'s args, then each of its mounts' `init`, through the same `MountSteps.run` traversal a push uses, as a parent's push runs a mounted component. Then `seed` runs. The session's runtime is `TestComponent.ComponentRuntime`, which has no `withIdentity`, since a component never sees its caller's identity.

The test adds no backend function. A slot's handle names the session's sink. A call whose arguments break the slot's contract is refused before anything holds it, as the binary refuses a handle's call: with an `Error` whose message is the binary's `ArgumentValidationError`. An answer that breaks the slot's declared return fails the call the same way, with the binary's `ReturnsValidationError`, so a `returned` answer to a slot that returns an id fails, since a drawn string is no id. Both checks are the binary's: an object's fields in key order, each missing required field where its key falls, a literal's own message, and an id read by its table number in the subject's root namespace, which stands in for the host's. An id from another component's table can name a different table there, as on a deployment, and a system table's id is refused as from a system table. An id the session did not mint, such as one from another session, names its own table there. A seeded differential on the local backend compares the two. A call to it during `init` or `seed` returns at once. Every later call, including a scheduled job that runs a stored handle, is held as a pending `{ kind: "callback", slot, input }` command, and the component's call waits until the test answers it. `TestComponent.commands(subject)` lists the pending commands, and `TestComponent.answer(command, outcome)` settles one. `returned` gives a value drawn from the contract's return codec, and a declared error tag gives an error drawn from that alternative's codec. Both draws use the session's `draws` seed, and a declared error crosses as Convex JSON, as the binary sends it. Between a call and its answer, the test can make other calls.

Three limits follow, and a test pins each. The kernel numbers each component's tables as a fresh push does: tables with an index of any kind first, staged ones included, then the rest, each group in name order. A deployment whose tables were dropped, or added by a later push, numbers them otherwise, since a table keeps its number, so there an id from another component can name a different table than the kernel says. `v.function()` takes each side's own handle format only: the kernel refuses a deployment's handle, and a deployment refuses the kernel's. And a kernel id carries its table's name but not its component: outside the session, or the restored snapshot, that minted it, an id from a child component names its own table in the root namespace, so its check against another component's `v.id` can differ from the binary's.

```ts
import { TestBackend } from "../confect/_generated/testing";

const install = {
  fromName: "Ada",
  onEvent: TestBackend.slots["mailer/onEvent"].handle,
};

it.effect("holds a delivery until the host answers", () =>
  Effect.gen(function* () {
    const t =
      yield* TestComponent.ComponentRuntime<typeof TestBackend.app.schema>();
    const sending = yield* Effect.forkChild(
      t.mutation(refs.public.mail.send, { message: "hi" }),
    );
    const [command] = yield* TestComponent.commands(TestBackend);
    // ... another call here sees the send uncommitted ...
    yield* TestComponent.answer(command, "Bounced");
    yield* Fiber.join(sending);
  }).pipe(Effect.provide(TestBackend.layer({ config, install }))),
);

const answered = TestComponent.callbacks(TestBackend, {
  "mailer/onEvent": {
    returned: {
      name: "delivers",
      call: "mail:send",
      args: { message: "hi" },
      postimage: { sent: [{ message: "hi", status: "delivered" }] },
    },
    Bounced: {
      name: "records the bounce",
      call: "mail:send",
      args: { message: "hi" },
      postimage: { sent: [{ message: "hi", status: "bounced" }] },
    },
  },
});
```

`TestComponent.exports` takes at least one case per function, and `TestComponent.callbacks` takes one case per slot per outcome, so a missing function or outcome does not compile. Each case pays its obligation and runs on a fresh session through `run({ config, install, seed })`. An export case states a literal return and the postimage, or one of the function's declared errors, and answers any callback its call makes `returned`. A callback case makes one exported call and answers each command that call makes to its slot with its outcome. It fails when the call never reaches the slot: a call `init` or `seed` made does not count. It then states the postimage. A postimage lists each table's documents without system fields, and a table it leaves out is empty. A case that does not hold fails `CaseFailed`, naming the case and the reason. When the session's packaged check refuses it, the refusal is its `cause`, `PackagedComponentChanged` or `PackagedLayoutUnsupported`, with its tag and fields, and `reason` holds the refusal's message. `TestComponent.laws(subject, seed)` pays `laws` and hands the laws to Frame's testing door, which checks them.
